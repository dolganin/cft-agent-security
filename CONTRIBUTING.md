# Разработка

## Перед изменениями

Прочитайте [AGENTS.md](AGENTS.md): это канонический контекст контрактов,
проверок, исполнения и Evidence. Рабочий код и тесты имеют приоритет над
историческими планами. Документация собрана в [docs/README.md](docs/README.md).

Создавайте рабочую ветку от актуальной `main`. Не включайте чужие локальные
изменения в свой коммит и не перезаписывайте существующие артефакты.
Изменения общих схем проверяйте вместе с их потребителями.

## Проверки

```bash
python -m pip install -e ".[dev]"
python -m pytest -q -rs
python -m ruff check .
python -m app.main
```

Если менялся интерфейс:

```bash
cd frontend
npm ci
npm test
npm run build
```

Для Docker/live-приемки нужны отдельные закрепленные образы, исходники и профили.
Не запускайте целевой код на хосте. Указывайте пропуски и их причины.
Unit-тесты не заменяют живую приемку, а скриптовая приемка не измеряет качество модели.

## Коммиты и данные

- Добавляйте в staging только файлы своей задачи; перед push проверяйте diff.
- Не публикуйте `.env`, ключи, окружения, зависимости, кэши и runtime-базы.
- Для результатов публикуйте отчет, протокол, необходимый пакет и SHA256.
- Не удаляйте Evidence и замороженные benchmark inputs как временные файлы.
- Не меняйте эталон или matching ради улучшения показателей.
- Отделяйте обнаружение от подтверждения, source proof от runtime proof,
  лабораторное время исправления от эксплуатационного MTTR.

Новая документация должна объяснять назначение, запуск, проверенный результат
и ограничения. Промпты завершенных разовых ИИ-заданий не нужны в основной
документации. Исторические отчеты сохраняйте по прежним адресам: они могут быть
частью воспроизводимых контрактов и командных ссылок.
