# B03: расширенный самостоятельный поиск по исходникам

Статус: B03 закрыта для DEV-сравнения source-discovery. Итоги, ограничения и
воспроизведение описаны в [отчете приемки](b03-acceptance-2026-10-14.md).
Runtime-подтверждение находок в этот этап не входило.

Обновление: несовместимость offline-проверки с развитием кода устранена через
[разделение historical/live](benchmark-history-and-stage-b.md). Исторический
замок не изменен. Реальный DEV-прогон завершен и сохранен; он не является
runtime-верификацией или проверкой HOLDOUT.

## Что изменено

- `round_robin` остается режимом по умолчанию с прежними бюджетами.
- Новый режим `handlers` ставит известные handler-файлы Express впереди остальных,
  затем читает окна вокруг обработчиков ввода, SQL, HTML, файловых операций,
  проверок прав и криптографических операций. До четырех приоритетных окон на файл.
- После приоритетных окон остается обход остальных строк; это не обещание полного
  чтения проекта в ограниченном бюджете.
- Относительные импорты из индексированного корпуса дают до 16 автоматических
  follow-up-файлов за запуск. Никакой загрузки пакетов или исполнения кода.
- Очередь дополнительных запросов чередуется с плановыми окнами. Модель сохраняет
  возможность запросить конкретные строки и буквальный поиск символа.
- Сохраняются непросмотренные диапазоны, полностью просмотренные файлы, причины
  остановки, число логических вызовов и задержка каждого ответа.
- PEM private keys маскируются до контекста модели с сохранением нумерации строк;
  исключены plural benchmark/fixture-каталоги и test/spec-файлы всех поддерживаемых
  расширений. Это усиление фильтров, не гарантия обнаружения всех секретов и подсказок.
- Инструкция разделяет weak-cryptography и authentication. Эвристика порядка чтения
  не присваивает вердикты или семейства находкам.

## Как включать

В каноническом конвейере: `CFT_SCOUT_SCHEDULE_MODE=handlers`.
Для отдельного исследования на операторском checkout:

```bash
python -m app.scout --target /path/to/approved/checkout \
  --output-dir artifacts/b03-dev-scout-new \
  --schedule handlers --max-turns 8 --max-candidates 32 \
  --max-source-chars 160000 --wall-clock-seconds 240 \
  --sast-findings /path/to/saved-canonical-findings.json
```

Папка результатов должна быть новой: существующий отчет не перезаписывается.
`--sast-findings` принимает JSON-массив канонических `Finding`, а не сырой Semgrep
JSON и не FinalReport. SAST-очередь не передается модели, только объединяется после
поиска через существующий нормализатор. Без этого файла standalone-режим не дает
сравнения с настоящим SAST: `baseline_supplied=false`.

`summary.json/sast_vs_sast_scout` показывает исходный размер SAST-очереди,
объединенный размер и дополнительные кандидаты. Это сравнение обнаружения кандидатов,
не Precision/Recall и не число подтвержденных уязвимостей. Кандидаты проходят прежний
контур Validator → Executor → Evidence. Для итоговых метрик нужен scorer A05.

## Бюджет и стоимость

Число ходов, новых символов, кандидатов, корпус и окна по-прежнему ограничены.
Таймаут выполняющегося HTTP-запроса и резервные маршруты могут выйти за общий срок,
как и в прежнем Scout. Логические вызовы и время измеряются; денежная стоимость и
token usage отмечаются `null`, поскольку текущий provider adapter их не возвращает.
Не заменяем измеренную стоимость оценкой по длине строк.

## Проверка и следующий шаг

Контролируемые тесты проверяют чтение важного участка после 300-й строки при
одинаковом ограниченном бюджете, неизменность legacy-порядка, маршрутный приоритет,
ограничение follow-up, справедливость очередей, маскирование ключей, непросмотренные
диапазоны и отказ считать неуспешный ответ просмотром. Standalone-проверка подтверждает,
что baseline не попадет в модель и сохраненный отчет не будет перезаписан.

Синтетические тесты проверяют только механику очередей и ограничений. DEV-приемка
на Juice Shop уже выполнена и описана в
[отчете B03](b03-acceptance-2026-10-14.md): там сохранены source snapshot, модельные
ответы, SAST baseline, candidate bindings, scorecards и ручная source review.
HOLDOUT не открывался; дополнительные кандидаты не проходили каноническую runtime-
верификацию, поэтому результат остается сравнением обнаружения кандидатов.

## Совместимость с историческим замком A01

Замок `juice-shop-v20.2.0-v2/protocol.yaml` закрепляет хеши исторических файлов.
B03 меняет Scout и индексатор, поэтому старый live replay намеренно не принимает
новую реализацию; историческая offline-проверка читает закрепленные Git-объекты.
Замки не переписаны. Для совместимости с A02 историческая сборка source map по
умолчанию сохраняет два служебных controller-файла в диагностическом списке,
но все живые Scout/API вызовы явно передают
`include_oracle_controllers=False`; сам `RepositorySource` по умолчанию их не
читает. Это не передает oracle-файлы модели.
