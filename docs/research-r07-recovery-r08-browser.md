# R07 recovery и R08 browser: реализация и приемка

## Итог

R07 больше не останавливает всю очередь из-за одного невалидного ответа модели.
R08 добавляет управляемый Chromium в существующий исследовательский граф.
Это разработка и функциональная приемка; R09 и R10 здесь не выполнялись.

## R07: что исправлено

1. Ответ остается строго проверяемым; одна ограниченная попытка исправления не
   меняет разрешения. Сохраняются ошибки как первоначального, так и исправленного
   ответа. В публичной диагностике остаются расположение поля и тип ошибки, без
   полного ответа и секретных значений.
2. В инструкции явно разделены пути `/target` для чтения из скрипта и `/workspace`
   для его выполнения, происхождение SHA256 и существующие observation IDs.
3. Неудачный вопрос сохраняет отчет и статус `failed`. Следующий получает только
   оставшиеся общие бюджеты: API-вызовы, действия, HTTP, время и объемы данных.
   Пропуск вопроса не считается успехом и не превращается в `rejected`.
4. Отказ доступа, оплаты, лимит провайдера или отсутствующая модель завершают
   кампанию с `provider_unavailable`. Три последовательных сбоя завершают ее с
   `consecutive_model_failures`. Счетчик сбрасывается после нормально выполненного
   вопроса. Очистка окружения остается обязательной.
5. Итог содержит `model_failures` и `degraded`. Даже если очередь дошла до конца,
   незавершенные вопросы видны. Строгая DEV-приемка не становится зеленой только
   потому, что после ошибки удалось выполнить следующий вопрос.

Модель не стала гарантированно выдавать корректные ответы. Исправлен механизм
работы с ними. В R09 отдельно измеряем долю незавершенных вопросов и причины.

## R08: как устроено

```text
ResearchTurn.browser_interact
  -> ActionProposal + digest операторского scope
  -> Validator
  -> SafeExecutor
  -> Chromium: Docker, network=none
       -> запрос ресурса по приватному каналу
       -> повторная проверка пути, метода и общего HTTP-бюджета
       -> фиксированный HTTP-работник во внутренней Docker-сети
       -> закрепленный контейнер цели
  -> DOM / диалоги / сетевой журнал / снимок
  -> execution + audit
  -> журнал наблюдений модели
```

Модель выбирает локальный путь, fragment и до восьми действий `fill`, `click`,
`press`, `snapshot`. Селектор должен однозначно указывать элемент; перед выбором
нужно изучить DOM. DOM-проекция содержит ограниченный текст и сведения об элементах,
но не значения полей, cookie или localStorage. Каждый вызов создает свежий анонимный
контекст; связанные действия формы помещаются в один вызов.

Произвольных `evaluate`, JavaScript-команд, CDP, URL origin, настройки браузера,
передачи storage state или подключения пользовательского браузера нет. Фиксированный
код работника использует собственную DOM-проекцию. Страница вправе выполнять свой
JavaScript, но у Chromium физически нет сети. Внешние обращения, WebSocket,
service workers и всплывающие окна не получают обходного доступа.

Доверенный транспорт перед каждым отправленным запросом и после ответа проверяет
контейнер, образ, IP и идентификатор внутренней сети. Полная проверка сети выполняется
до и после браузерного действия. Origin в браузере виртуальный; сетевой адрес выбирает
только операторский реестр. Заголовки Authorization/Cookie не принимаются от модели.
POST/PUT/PATCH/DELETE доступны только на явно разрешенных оператором путях.

Браузер и транспорт непривилегированные, с read-only root, ограничениями CPU,
памяти и числа процессов. Docker socket и файлы хоста им не выдаются. Скриптовый
контейнер остается отдельно, тоже без сети. Все временные контейнеры удаляются,
даже при сбоях промежуточной очистки; неизвестная очистка не считается успехом.

### Бюджеты

- До 64 ресурсных запросов на браузерное действие.
- До 2 MiB на один ресурс и 16 MiB переданных ресурсов на действие.
- До восьми UI-шагов, ограниченные снимки DOM/диалоги; PNG до 1 MiB.
- Общий HTTP-бюджет ResearchRuntime по умолчанию 128 при явном подключении браузера,
  иначе прежние 32. Оператор может задать `max_http_requests` (0–256).
- CampaignLimits имеет общий `max_http_requests` (по умолчанию 256). Новый вопрос
  не восстанавливает израсходованный бюджет.
- `action_timeout` по умолчанию прежние 10 секунд; для браузера Juice Shop в
  операторской конфигурации задается 30. Общий лимит кампании также действует.

HTTP-работник живет весь срок одного действия. Это устраняет запуск нового Docker
процесса для каждого JS/CSS-файла без расширения сетевых разрешений. IPC асинхронный,
но запросы к транспорту сериализованы: одновременные запросы страницы не перепутывают
ответы. Версия SDK/Chromium закреплена в
`executor/research_browser.Dockerfile`; основа и рекомендации:
[Playwright Docker](https://playwright.dev/python/docs/docker),
[перехват запросов](https://playwright.dev/python/docs/network).

## Границы этой версии

- Это браузерные **наблюдения**, не универсальный независимый verifier для XSS/CWE.
  DOM, alert или screenshot модели сами по себе не дают `confirmed`.
- Аутентифицированные браузерные роли, перенос cookie/localStorage между вызовами,
  downloads, iframe-взаимодействия и произвольные script/evaluate не включены.
- HTTP redirects не следуются автоматически, даже локальные. Следующая навигация
  должна быть отдельным одобренным действием. Это сохраняется в сетевом журнале.
- Виртуальный origin, отсутствие cookies и ограниченные заголовки могут менять
  поведение приложений, зависящих от точного origin/сессии. Это не бинарная аттестация
  исходников контейнера. Нельзя выводить безопасность из неподдержанного поведения.
- Страница может не успеть завершить загрузку или исчерпать ресурсный бюджет.
  `navigation_complete`, `network_settled`, ошибки и сетевой журнал остаются в
  наблюдении; наличие PNG не доказывает полноту загрузки.
- Для R09 профиль должен независимо задавать разрешенные пути и исключать
  benchmark oracle/scoreboard/решения. Producer не получает эталонные ответы.
- Скриншоты включаются явно. Они могут содержать данные цели; перед публикацией
  чужих результатов их нужно просмотреть. Проверенные здесь цели локальные и учебные.

## Приемка

В R07 специально подается неправильный ответ и неправильное исправление. Реальные
LangGraph и Docker сохраняют неудачный вопрос, выполняют следующий и не выдумывают
подтверждение. Провайдер в этой проверке синтетический, API не расходуется.

R08 проверяется на отдельном управляемом UI fixture, не на модифицированном Juice
Shop. Одинаковый безвредный маркер вызывает dialog в варианте с небезопасным DOM sink,
но остается текстом в безопасном варианте. Проверяются запрещенный путь, внешние
переходы, PNG SHA256, очистка, канонический граф и отсутствие автоматического verdict.

Отдельный smoke открывает закрепленный Juice Shop v20.2.0, получает DOM и PNG,
проверяет исходный snapshot и удаляет окружение. Это **не** поиск уязвимостей и
не измерение Precision/Recall. Модель в браузерной приемке — тестовый клиент;
качество живого выбора действий Qwen предстоит измерить в R09.

Неуспешные технические попытки сохранены отдельно: первоначально был указан
неверный локальный image ID; затем обнаружены синхронное зависание, слишком малый
лимит размера JS-ресурса и накладные расходы Docker. Они не выдаются за успешные
повторы. Промежуточная полная проверка: 1280 passed, 19 skipped; Ruff тогда нашел
порядок импортов, который исправлен. Окончательные результаты находятся в пакете.

## Запуск и перенос

```bash
docker build -f executor/research_browser.Dockerfile -t cft-research-browser:r08 .
docker image inspect cft-research-browser:r08 --format '{{.Id}}'
python -m app.research_recovery_acceptance --image <immutable-research-image> \
  --output artifacts/<fresh-recovery>
python -m app.research_browser_acceptance --image <immutable-research-image> \
  --browser-image <immutable-browser-image> --output artifacts/<fresh-browser>
python -m app.research_browser_juice_smoke --image <immutable-research-image> \
  --browser-image <immutable-browser-image> \
  --checkout artifacts/benchmark-target/juice-shop --output artifacts/<fresh-juice-ui>
```

В `app.research_campaign` / `app.research_run` операторская конфигурация дополнительно
содержит `browser_image`, `action_timeout: 30` и `max_http_requests: 128`. Сервисы,
HTTP grants, источник и образ исследовательского контейнера задаются как ранее.
`denied_prefixes` в grant сервиса имеет приоритет над разрешенными префиксами,
включая многократно URL-encoded пути. Smoke явно исключает `/socket.io`,
`/rest/challenges`, `/score-board`: фоновый polling не нужен для осмотра UI,
а challenge/scoreboard не должны подсказывать агенту эталонные ответы.
Нужен существующий Docker lab, не URL произвольного сервера. Mutable tag допустим
только на этапе provisioning: для исполнения используется полученный immutable ID.
ID локальной сборки зависит от архитектуры; на другом ПК образ пересобирается и его
ID заново фиксируется. Образы Docker в evidence ZIP не входят.

Переносимый пакет содержит sealed результаты, журналы, PNG, диагностику неудачных
попыток, Git/source provenance и SHA256. Среды, исходники цели и ключи не публикуются.
Для проверки целостности без Docker/API:

```bash
unzip -t artifacts/handoffs/research-r07-r08-2026-10-15.zip
python -c 'from pathlib import Path; from app.research_handoff import verify_seal; print(verify_seal(Path("artifacts/<extracted-result>")))'
```

Seal доказывает неизменность данных, не истинность интерпретаций. Повторение
браузерного эксперимента требует Docker и закрепленной цели; один screenshot
не позволяет офлайн заново выполнить страницу.

## Дальше

Следующий заход: R09, один диагностический DEV-прогон с живой моделью, браузером,
общими бюджетами и картой потерь. По его результатам выбираем улучшения и только
после freeze выполняем R10. Воспроизводимость и MTTR здесь не заявляются.

  UI отрисован, но полная загрузка всех фоновых ресурсов не заявляется.
- `r07-r08-release-code-verification-2026-10-15`: окончательные pytest/Ruff/graph/
  Docker-loop/diff-check: **1285 passed, 19 skipped**, Ruff PASS, прежний граф PASS,
  отдельный Docker-loop **21 passed**, diff-check PASS. Пропуски перечислены в
  `unit-suite.log`: исторические opt-in интеграции с отдельными образами/целями,
  Stage1 и проверки с операторскими наборами данных. Они не объявляются выполненными.

Предыдущие sealed попытки не перезаписываются. Для незавершенных технических
диагностик `app.research_result_seal` добавляет только маркировку development attempt
и seal, не меняя исходные файлы. Неудачные попытки остаются неудачными.

Chromium здесь изолирован Docker, а не объявлен дополнительной независимой
границей безопасности. Внутренний Chromium sandbox не включался отдельно; этот
контур предназначен только для согласованных локальных учебных/тестовых целей.
Режим не предназначен для посещения произвольных недоверенных сайтов интернета.
