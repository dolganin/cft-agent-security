# CFT Security Agent: что изменилось после работы с Juice Shop

Дата: 8 октября 2026.

Этот документ сравнивает нашу новую версию с состоянием локального `main`
до сегодняшнего переноса изменений. Он описывает работающий код, а не все
пункты планов разработки.

Состояние GitHub и локального `main` не тождественно: текущий перенос выполнен
локально. Этот документ сам по себе не означает, что сделан push.

## 2. Коротко: главное отличие

Раньше агент уже умел разбирать находку сканера, учитывать архитектурный
контекст, формировать гипотезу и проверять ее через Validator, Executor и
Evidence. Но исследование репозитория было слабым: отдельный Scout видел
перечень файлов и технологические сигналы, а не сами исходники.

Теперь Scout читает ограниченные окна реального кода, может запросить
дополнительное чтение и буквальный поиск, сохраняет область исследования
и передает привязанные к исходникам гипотезы в общую очередь. Для некоторых
SQL- и файловых проблем добавлены конкретные проверки. Результат можно
показать в интерфейсе вместе с вызовами инструментов и доказательствами,
а для одного подтвержденного SQL-случая получить предложение исправления.

Это переход к более проверяемому прототипу. Это еще не универсальный
автономный пентестер и не агент, который надежно исправляет весь проект.

## 3. Сравнение возможностей

| Область | В старом `main` | В нашей версии |
|---|---|---|
| Scout | Один запрос по inventory: файлы, сигналы, компоненты | Несколько ограниченных шагов с пронумерованными окнами исходников, чтением и буквальным поиском |
| Привязка кандидата | Файл должен принадлежать inventory | Кандидат должен ссылаться на реально прочитанные строки; заявленные provenance-файлы тоже должны быть прочитаны |
| Учет исследования | Нет детальной картины чтения исходников | Диапазоны чтения, уникальные строки, бюджет, причины исключения и остановки |
| Discovery | Список файлов был связан с технологическими сигналами | Передает полный обнаруженный список файлов; Scout затем применяет свою политику допуска |
| Express | Нет отдельной карты source routes | Ограниченная карта прямых регистраций, middleware и импортированных файлов обработчиков |
| Объединение находок | Простая проверка совпадения rule/file/line | Общие семейства правил, пересечение диапазонов, стабильные ID Scout и учет дублей |
| Проверка JavaScript | Общий sandbox и ранее существующие инструменты | Дополнительное ограниченное чтение source metadata для JS/TS |
| SQL | Нет новых специализированных возможностей этой версии | Source-проверка прямой интерполяции и ограниченные runtime differential checks для разрешенных login/search endpoints |
| Открытые каталоги | Общие HTTP-наблюдения | Проверка доступного списка чувствительных имен без скачивания содержимого |
| Связь finding → endpoint | Общие разрешения и профили | Точная операторская привязка файла, строки, режима, сервиса и endpoint для новых runtime-проверок |
| Планирование | Модель могла вернуть план нескольких действий | Одна следующая проверка на итерацию; перед следующей пересматриваются накопленные Evidence |
| Исчерпание проверок | Для нового JS-пути не было отдельного штатного выхода | Нет неиспользованных зарегистрированных действий → `inconclusive` с объяснением |
| Диагностика модели | Не было нового постоянного журнала попыток | Provider, model, операция, статус, задержка и события fallback записываются без ключей |
| Интерфейс | Чат, прогоны, отчеты и инструменты уже были | Экран `/demo`, стадия Scout, новые вызовы инструментов и предложение diff |
| Исправление | Была отдельная заготовка proposal/verification | Добавлен доступный из демо review-only процесс для одного SQL-случая; применения и runtime-проверки патча пока нет |

## 4. Что конкретно доработано

### 4.1. Поиск модели по настоящим исходникам

Основные компоненты: `agent/repository_scout.py`,
`tools/repository_source.py`, `app/scout.py`, `schemas/scout.py`.

Scout теперь может:

1. Получить ограниченный корпус application source из доверенного Discovery.
2. Прочитать окна с физическими номерами строк.
3. Запросить дополнительные окна и поиск буквальной строки.
4. Учитывать ранее прочитанный контекст в следующих шагах.
5. Предложить кандидата с source anchor и provenance.
6. Сохранить отчет о фактическом охвате и причине остановки.

Из модельного корпуса исключаются окружения, зависимости, сборки,
тестовые/эталонные каталоги и учебные решения. Из строк удаляются
benchmark-аннотации и маскируется часть секретных литералов. Это не гарантия
обнаружения всех секретов и не полное чтение репозитория.

Есть ограничения числа ходов, исходного текста, кандидатов и времени.
Временной бюджет проверяется между ходами; он не равен жесткому прерыванию
всех сетевых запросов точно на границе бюджета.

### 4.2. Ограниченная карта Express

Новые компоненты: `discovery/express_routes.py`, `schemas/source_map.py`.

Карта фиксирует распознаваемые регистрации маршрутов, метод, статический
путь, строку, порядок middleware и связанные импортированные файлы.
Она передается Scout и сохраняется вместе со связями кандидатов с routes.

Это лексический разбор поддержанных конструкций, не полноценный AST-анализ
всего приложения. Наличие маршрута в карте не доказывает отсутствие
авторизации. Динамические пути и неоднозначные связи отмечаются отдельно.
Карта не дает агенту разрешения обращаться к произвольному endpoint.

### 4.3. Новые инструменты проверки

Добавлены зарегистрированные возможности:

- `inspect_javascript_security` — ограниченная source-проверка. Метаданные
  исходника сами по себе не доказывают эксплуатацию. Специальный режим
  интерполяции может подтвердить конкретное source-условие, но не runtime exploit.
- `verify_sql_injection` — ограниченное сравнение повторных проверочных
  запросов с повторными отрицательными контролями. Режим и endpoint задает
  доверенный профиль, не модель.
- `verify_sensitive_directory` — наблюдение за списком имен и типами файлов
  в разрешенном каталоге. Содержимое чувствительных файлов не скачивается.

Результаты новых инструментов имеют структурированный контракт
`BoundedVerificationResult` и отдельные типы Evidence. Простая строка
`confirmed` в stdout произвольной команды не считается достаточным доказательством.

Основные файлы: `agent/verification.py`, `executor/executor.py`,
`executor/worker.py`, `validator/validator.py`, `evidence/interpreter.py`,
`schemas/security_tools.py`, `policies/default.yaml`.

### 4.4. Границы исполнения и устойчивость

Для новых активных проверок сохранена цепочка:

```text
Гипотеза модели → ActionProposal → Validator → Executor → Evidence → вывод
```

Validator дополнительно проверяет artifact, строку, разрешенный тип проверки,
сервис, endpoint и SQL-режим. Агент не выбирает произвольный URL или host path.

Target-network инструменты направляются в Docker с доверенной runtime-картой.
Общий `sandbox_command` остается networkless и не получает эту сеть.
В аудит записывается фактический backend и сетевой режим исполнения.

В startup readiness теперь различаются исходные компоненты проекта и
реальные сервисы Compose. Например, отдельный frontend package внутри
готового образа Juice Shop не должен ожидаться как второй контейнер.
Ошибочная явная привязка Compose service диагностируется до старта.

Диагностика запуска Docker runner стала содержательнее. Идентификаторы
действий дополнены digest, чтобы разные длинные finding ID не превращались
в одинаковые action ID после обрезки. Это не означает, что исправлены все
возможные коллизии исходных записей сканера.

При исчерпании разрешенных новых JS-проверок агент завершает проверку
с недостаточными данными, а не пытается выдумать новый инструмент.
Это не обещание отсутствия любых технических сбоев.

### 4.5. LLM, отчеты и интерфейс

Добавлен постоянный журнал фактических обращений к модели и fallback.
Увеличены бюджеты выходного JSON; Scout получает оставшийся лимит кандидатов.
Для NSU адаптировано значение уровня reasoning, передаваемого провайдеру.

Для демонстрационного сервера явно выбран NSU `Qwen3.8-27B`.
Он реально ответил в проверенном прогоне 8 октября. Это не означает,
что DeepSeek тоже работал: при диагностике его запрошенный идентификатор
получал `Model not found`. Ключи в Git не включены.

Добавлены:

- экран `/demo` с объяснением продукта и настоящим результатом запуска;
- отдельный сервер `python -m app.demo`, профиль Juice Shop и Compose template;
- стадия Scout: просмотренные файлы, кандидаты, причина остановки;
- отображение новых инструментов с endpoint, параметрами, выводом и сессией;
- явное отличие вызова зарегистрированного инструмента от shell-команды;
- просмотр и скачивание предложения исправления.

Демо вызывает канонический CI pipeline. Это не вторая реализация анализа.
Оно использует отдельные базу и каталог результатов, не заменяя прежние
измерения. Два выбранных правила Semgrep и короткие бюджеты делают его
ограниченной демонстрацией, а не полным бенчмарком.

### 4.6. Предложение патча: первый шаг, не готовое автоисправление

Новые компоненты: `fix_verification/review.py`, `PatchReviewArtifact`,
demo API и `PatchProposalPanel`.

В интерфейсе можно попросить модель предложить минимальный diff для
подтвержденной SQL-находки `routes/search.ts:23`. Проверяются:

- подтвержденный отчет с Evidence и совпадение выбранного условия в исходнике;
- разрешенный файл и окно изменений;
- точные контекст, смещения и счетчики unified diff;
- запрет иных файлов, symlink paths, rename/binary/mode metadata;
- ограничение размера и признаки credential/redaction content;
- сохранение поддержанного SQL-шаблона и согласованность placeholder/options;
- digest текущего файла и предложения.

Первая попытка модели смешала `:criteria` с `bind`. Она не стала проверенным
исправлением: при ревью ошибка обнаружена, добавлена проверка формата,
а предыдущий артефакт сохранен как отклоненный. Второе предложение использует
`:criteria` с `replacements` и прошло review checks и `git apply --check`.

Исходный проект не изменялся. Патч не применялся, измененная программа
не собиралась и не тестировалась. Поля `applied` и `security_verified`
равны `false`; исходный Gate остается прежним.

Старая заготовка `FixVerificationService`, способная запускать проверки
на хосте, к новому demo-пути не подключена. Следующий этап — применение
в отдельной Docker-копии, функциональные тесты и повтор исходной проверки.

- Frontend suite: **27 passed**.

проверок также не включен в новую версию.

## 7. Что уже было в main, а не создано сейчас

Не нужно представлять как новую разработку этого этапа:

- базовый LangGraph и shared schemas;
- SAST, контекстный приоритет и разделение с CVSS;
- LLM reasoning adapter и цепочка provider fallback;
- Validator, Executor, Docker sandbox и Evidence guard;
- общий `sandbox_command`, HTTP-наблюдения и source-проверки Docker/Python/React;
- API, чат, импорт проектов, удаление чатов, отчеты и отображение действий;
- отдельную заготовку patch proposal/verification.

Еще в интеграции `9266e1d` пришли командные autonomy v2, начальный
inventory-only Scout, стабилизация SAST/LLM, Compose retries и обновление
документации. Наш этап расширяет эту основу, а не создает весь агент с нуля.

## 8. Что остается незавершенным

1. Полный coverage и recall по независимому эталону Juice Shop.
2. Сопоставимый DAST baseline и несколько одинаковых полных прогонов.
3. Независимая точность вердиктов, CVSS и Context Priority.
4. Полноценные AST/interprocedural связи и доказательная проверка авторизации.
5. Более широкие runtime-проверки, включая XSS и ownership controls.
6. Безопасное применение патча, сборка и before/after verification в Docker.
7. Автоматический PR/review workflow после проверенного исправления.
8. MTTR: нет истории реально принятых исправлений; время анализа и время
   подготовки diff не являются MTTR.

## 9. Как кратко объяснить разницу на презентации

> Раньше основа агента уже обрабатывала предупреждения сканера и проводила
> разрешенные проверки. Мы доработали самостоятельное исследование реального
> кода, учет охвата, ограниченную карту Express и конкретные проверки SQL
> и файловых поверхностей. Теперь можно показать не только итоговый вердикт,
> но и путь от исходника до действия и доказательств. Добавили первый шаг
> к исправлениям: модель предлагает diff, система проверяет его область
> и формат, разработчик может его посмотреть и скачать. Автоматическое
> применение и повторную проверку патча еще предстоит довести.

Сценарий показа: [демонстрация на 3–5 минут](demo/README.md).

## 10. Как проверить сравнение по Git

Команды выполняются из корня репозитория:

```bash
git show --stat 9bb467a
git diff --name-status 9266e1d 9bb467a
git diff 9266e1d 9bb467a -- agent discovery executor validator evidence schemas frontend
git log --oneline c19b404..9266e1d
```

Новый файл сравнения добавляется отдельным документационным коммитом.
Указанный `9bb467a` остается фиксированной точкой сравнения кода, даже если
позднее `main` продвинется дальше.
