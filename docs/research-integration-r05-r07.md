# R05–R07: интеграция исследовательского агента

Итог: R05 и узкие R06-протоколы реализованы; минимальная живая R07-проверка
пройдена. Приемка длинной многовопросной кампании остается частичной из-за отказов
структурированных ответов. Это ограничение не закрыто успешным одним сценарием.

## Что реализовано

R05 объединяет входы SAST, DAST, кандидаты модели и вопросы по еще не изученным
обработчикам в ограниченную очередь. Повторные наблюдения сохраняются в provenance,
но не создают отдельные одинаковые находки. DAST может передать наблюдение по
зарегистрированному сервису и локальному endpoint без выдуманного номера строки.
Вопрос по поверхности приложения сам по себе не считается уязвимостью.

Модель выбирает чтение файлов, поиск по замороженному перечню исходников, запись
Python/Node-скрипта, его запуск в Docker и разрешенный HTTP-запрос. Каждое действие
проходит существующие Validator, Executor, сохранение execution и audit. Исходный
проект доступен только для чтения; модель не выполняет команды на хосте. Поиск по
папке раскрывается только в уже разрешенные файлы, не расширяя область доступа.

Кандидат модели должен ссылаться на реально прочитанный диапазон строк и точный
фрагмент. Неизвестные ссылки в ответе модели отклоняются; одна заранее учтенная
попытка исправления структурированного ответа не ослабляет ограничения. Ошибки
скрипта могут стать наблюдением следующего шага, но не доказательством уязвимости.

R06 добавляет два независимых протокола доказательства:

- `weak_digest_call.v1`: фиксированный AST-проверяющий подтверждает явно вызванный
  слабый алгоритм хеширования. Это факт исходного кода, не доказанная эксплуатация
  и не автоматическая оценка критичности. Комментарий, текстовая имитация вызова,
  неоднозначность или неизвестный алгоритм не подтверждают находку.
- `confidential_marker.v1`: оператор задает приватный маркер и положительный и
  отрицательный контроли. Фиксированный проверяющий повторяет наблюдение на двух
  свежих поколениях целевого контейнера и проверяет audit, идентичность, контроли
  и очистку. Пустой HTTP 200 не доказывает ни уязвимость, ни безопасность.

Подтверждение исходного кода получает канонический FinalReport только с совместимой
находкой, диапазоном и execution чтения. Новая обнаруженная причина получает свой
отчет, а не присваивается случайному исходному предупреждению сканера. HTTP-протокол
сохраняет самостоятельный результат; обобщенное семантическое сопоставление его
результата с любыми CWE пока не реализовано.

## Что это пока НЕ означает

Это не завершенный универсальный пентестер, не автоматическое исправление проекта
и не новый результат полного бенчмарка. SQL/IDOR и остальные существующие B-протоколы
не становятся автоматически доступными новой модели через эти два протокола.
Для неподдержанных свойств остается `review_pending`/`inconclusive`, а не ложный
`rejected`. Исторические настройки A/B, эталон, оценки и политики не изменялись.

Счетчик очереди не равен числу истинных уязвимостей. Покрытие чтения не равно Recall.
Скрипт, который печатает CONFIRMED, не подтверждает находку: решение принимает
независимый проверяющий, а не stdout или заключение модели.

## Проверки и сохраненные попытки

`artifacts/r05-r06-integration-acceptance-2026-10-15` содержит восемь успешно
проверенных свойств интеграции на реальном Docker: объединение наблюдений, положительный
source-контроль, канонический отчет, покрытие чтения, уязвимый и безопасный HTTP-контроли
и свежие поколения. Модель в этой проверке синтетическая; это не метрики Juice Shop.

Точная причина последней ошибки недоступна из старого отчета: сообщение границы
ошибки было общим. Это не объявляется ошибкой авторизации и не списывается на NSU
без доказательств. Добавлена безопасная диагностика стадии принятия ответа и
контекстная проверка реальных observation IDs внутри механизма исправления ответа.
После этой доработки отказ на третьем вопросе уже локализован в проверке ответа
провайдера (`provider_response_validation`, `schema_validation_failed`), не в
Docker или авторизации. Минимальный сквозной сценарий запускается отдельно с
явным `--max-questions 1`; его нельзя выдавать за приемку всей длинной кампании.

R07 использует закрепленный Juice Shop v20.2.0, коммит
`5658473cf8814459bf89000ce373b20ed0b4eb37`, модель `nsu:qwen3.8-flash-next`.
Функциональная DEV-проверка сохраняет все 95 исходных SAST-наблюдений и выбирает
представителей семейств. Приоритет weak-cryptography задан явно для проверки
реализованного source-протокола: это калибровка функциональности, не независимая
оценка полноты поиска. Бюджеты: максимум 4 вопроса, 32 действия, 36 API-вызовов,
480 секунд кампании; в вопросе до 8 действий и 180 секунд. Исправления ответа
учитываются в API-вызовах. IO-reservation не является стоимостью в токенах.

Финальная интеграционная проверка сохранена отдельно в
`artifacts/r05-r06-final-acceptance-2026-10-15`: снова 8/8 PASS. Промежуточный полный
набор: 1266 passed, 19 skipped; отдельный Docker-loop: 20 passed. Окончательные
логи после последних изменений находятся в
`artifacts/r05-r07-published-code-verification-2026-10-15`.
Их итог: 1267 passed, 19 skipped, Ruff PASS, прежний граф PASS, Docker-loop 21 passed,
diff-check PASS. Пропуски перечислены в `unit-suite.log`: старые opt-in Docker/
SberLab/Autodealer/Stage1-проверки и проверки с отдельными операторскими данными;
они не объявляются выполненными. Актуальный research Docker-loop проверен отдельно.

Минимальный живой сценарий остановлен лимитом восьми действий, а не ошибкой модели.
Один независимый положительный source-результат не является долей Precision или
показателем общего Recall. Исправленный скрипт анализировал наблюдения и запускал
свой эксперимент; его текстовые заявления об impact не считаются доказанными.
Исходники не изменены, очистка Docker подтверждена. Полный многовопросный режим
остается приоритетной доработкой R09, как и увеличение числа независимых протоколов.

## Воспроизведение

Из корня проекта, с установленными dev-зависимостями и Docker:

```bash
PYTHONDONTWRITEBYTECODE=1 python -m app.research_loop_verify \
  --output artifacts/<fresh-code-verification> --image <immutable-research-image-id>
PYTHONDONTWRITEBYTECODE=1 python -m app.research_integration_acceptance \
  --output artifacts/<fresh-r05-r06-acceptance> --image <immutable-research-image-id>
PYTHONDONTWRITEBYTECODE=1 python -m app.research_dev_acceptance \
  --checkout artifacts/benchmark-target/juice-shop \
  --output artifacts/<fresh-live-dev> --image <immutable-research-image-id> \
  --max-questions 1
```

Живой запуск требует действующий `NSU_OPENWEBUI_KEY` через приватное окружение.
Ключи в архив не входят. Использованные неизменяемые образы указаны в manifests;
работающий целевой контейнер не публикует порт на хосте. Любой новый запуск должен
использовать новую папку; это не восстановление старых одобрений или сессий.

Проверка целостности сохраненного пакета без Docker и API:

```bash
python -c 'from pathlib import Path; from app.research_handoff import verify_seal; print(verify_seal(Path("artifacts/<result-directory>")))'
unzip -t artifacts/handoffs/research-integration-r05-r07-2026-10-15.zip
```

Для повторного независимого AST-анализа нужны исходники того же закрепленного
коммита и их digest: одних итоговых JSON недостаточно для проверки содержания
источника. Seal подтверждает неизменность артефактов, а не истинность любой
интерпретации модели. Исходный checkout, среды, node_modules и секреты не публикуются.

Переданный ZIP содержит все перечисленные результаты и неудачные попытки,
SHA256-manifest и Git/source provenance. Архив не содержит исходники целевого
магазина, установленное окружение или токен. Его относительный путь:
`artifacts/handoffs/research-integration-r05-r07-2026-10-15.zip`.

## Следующий этап

После приемки механизма: расширять независимые протоколы и полезную поверхность
исследования, затем проводить отдельный полный прогон по замороженному эталону.
Только такой прогон дает сопоставимые Precision/Recall/FPR. Воспроизводимость и MTTR
в этой функциональной проверке не измеряются.
