# Исторический эталон и новая версия агента

Раньше `load_protocol()` проверял текущие Python-файлы по замку старого A01.
Любое развитие Scout нарушало эту проверку даже для offline-чтения старых результатов.
Теперь явно разделены две операции:

```bash
# Проверка исторического протокола и закрепленного кода, без исполнения
python -m evaluation.benchmark_protocol --baseline-mode historical

# Проверка точного живого повтора старой конфигурации
python -m evaluation.benchmark_protocol --baseline-mode live
```

Исторический режим — режим по умолчанию metadata-loader. Старый код читается из
фиксированной Git-ревизии `b8132589b0c21483b335e1529f8b81250dfb9b59`, затем сверяется
со всеми прежними SHA-256. Данные, YAML/JSON, benchmark source fixtures, документы
и не-Python входы проверяются в текущем checkout; их изменение по-прежнему запрещено.
A04 аналогично сверяет исторические Python-генераторы, не требуя исполнять их снова.
Нет переключения на свежие байты при отсутствии истории и нет перезаписи замков.
Нужна полноценная Git-копия с указанным объектом; source ZIP без Git не достаточен.

Историческое PASS подтверждает сохранность эталона, **не** совместимость запущенного
агента со старым baseline. Точный live replay обязан вызывать
`load_protocol(baseline_mode="live")` до запуска инфраструктуры/модели. В B03 этот
режим корректно отказывает: код изменился. Нельзя использовать историческое PASS
для присвоения новому прогону старой measurement identity.

Новая identity для Stage B формируется отдельно:

```bash
CFT_SCOUT_SCHEDULE_MODE=handlers python -m app.measurement_manifest \
  --output artifacts/b03-measurement-manifest-new.json
```

Команда фиксирует актуальные хеши реализации, target commit, dataset lock и разрешенные
несекретные настройки, включая режим Scout. Git HEAD записан как provenance, а точная
identity зависит от фактических байтов файлов, в том числе еще не закоммиченных.
Секреты не сериализуются. Существующий файл не перезаписывается. Manifest — не запуск,
не новые метрики, не разрешение игнорировать preflight и не полный протокол приемки.
Для нового прогона нужно привязать к нему сохраненные конфигурацию/артефакты и проверить
identity перед/после измерения. Сравнение B03 по DEV остается отдельной задачей.

приложения и тестов, измененных scripts и stub `python -m app.main` прошли.

sandbox manager targets/image (4), sandbox runner image (1), SberLab session (3),
Stage1 opt-in Docker E2E (1), старый Stage2 pinned checkout (1). Эти интеграции не
объявляются выполненными. Два предупреждения зависимостей не связаны с исправлениями.
Повторное дополнение A08 дает идентичную сводку; output/input seals перепроверены.
CI checkout агента переведен на `fetch-depth: 0`, чтобы фиксированная историческая
ревизия была доступна и на GitHub runner. Remote workflow здесь не запускался.
