# Серьезность и Context Priority: дополнение к свежему измерению

Серьезность теперь пересчитана по сохраненным доказательствам. **Совпадение с
имеющейся ordinal-разметкой: 3/3 = 100%; покрытие размеченных случаев: 3/4 = 75%.**
Это постфактум-расчет новой детерминированной функции, не оценка LLM из исходного
запуска и не точность CVSS. В оригинальном запуске нужные оценки не сохранялись.
Исходные результаты, timestamps и A04 lock не изменены. Новых целевых
HTTP-проверок, поисковых прогонов или обращений к NSU не выполнялось. Для отдельного
черновика CP использован слепой модельный рецензент, как описано ниже.

## Какие случаи оценены

| Случай A04 | Подтвержденное свойство | Оценка | Эталон |
|---|---|---|---|
| JS-AUTHZ-001 | Несанкционированное постоянное изменение товара с независимым readback | HIGH | HIGH |
| JS-AUTHZ-002 | Приобретение административной роли, проверенной после входа | HIGH | HIGH |
| JS-SQL-002 | Обход аутентификации с повторенными отрицательными/положительными контролями | HIGH | HIGH |
| JS-SQL-001 | Влияние на SQL-выборку; достаточный ущерб отдельно не установлен | UNASSESSED | HIGH |

Функция `scoring.runtime_impact.assess_verified_impact` не читает эталон, case ID,
severity сканера или модельные обоснования. Она принимает только заново
восстановленное каноническое Evidence и исходное ActionProposal. Права, вердикты,
FinalReport и Gate от этого расчета не меняются. Операторский B08 ScoringReview
с человеческим reviewed_by не создается и не подменяется.

Все четыре имеющиеся метки серьезности относятся к классу HIGH. Поэтому 100%
на трех выставленных оценках не показывает качество различения LOW/MEDIUM/HIGH
на широком наборе. Из 27 уязвимых случаев разметка серьезности есть только у
четырех; фактически сопоставимая оценка получена у трех. Неизвестные случаи не
объявляются низкой серьезностью. Подтверждение SQL injection само по себе не
доказывает извлечение конфиденциальных данных, запись в БД или другие impacts.

## Что сделано для Context Priority

У A04 по-прежнему **0 независимых CP labels**. В 46 сохраненных отчетах нового
прохода: 15 CP отсутствуют, 31 имеет статус partial; полных assessed-оценок нет.
Это числа отчетов, не независимых случаев. Точность CP остается N/A по двум
причинам: нет независимого эталона и нет полных оценок, совместимых с ним.

Подготовлен отдельный пакет на **35 original-случаев**:

- case ID, независимая группа и split;
- исходные source/HTTP anchors и SHA256 файлов закрепленного target;
- поля для независимого приоритета, объяснения, ссылок на факты и рецензента;
- отдельный файл известных архитектурных фактов и partial-предпросмотра CP.

В reference draft намеренно нет агентских приоритетов или автоматически
заполненных правильных ответов. Это **пакет для разметки, а не завершенный эталон**.
Он создан до постфактум-расчета, исходя только из замороженных anchors и исходников.

В исходниках установлено использование SQLite и MarsDB; факты привязаны к строкам
и SHA256 `models/index.ts` и `data/mongodb.ts`. Существующая функция CP дает на
одних этих фактах 2 балла и partial LOW. Это нижняя граница по известным фактам,
не окончательный вывод о низком риске. Она относится только к контексту backend
и не автоматически назначается всем находкам frontend или всем benchmark cases.

Неизвестны production exposure, бизнес-критичность активов, критические пути,
аутентификация конкретных маршрутов и blast radius. Изоляция измерительной
Docker-лаборатории не доказывает, что само приложение предназначено только для
непубличного использования. Эти поля не заполнены догадками.

## Дополнение: публичный магазин с реальными аккаунтами и заказами

Пользователь явно задал этот сценарий. Он используется только в новом постфактум
расчете, а не ретроспективно приписывается измерительной Docker-лаборатории.
`scoring.context_bounds` перебирает крайние значения неизвестных входов текущей
формулы CP. Уровень выставляется только если все допустимые значения дают один
уровень; неизвестные факты остаются неизвестными, полного числового рейтинга нет.
Для центрального backend получен интервал 9–10 (HIGH); для browser 5–8, поэтому
однозначный уровень не выставлен. Сам расчет не читает эталонные оценки.

Отдельный модельный рецензент получил 35 source-привязанных карточек и сценарий,
но не результаты агента, текущую scoring-формулу или ожидаемые оценки. Получена
разметка HIGH: 11, MEDIUM: 8, LOW: 2, null: 14. Ее статус
`draft_requires_human_review`: это не человеческий и не утвержденный эталон.
Ссылки содержательных оценок проверены на пересечение с замороженными source anchors.

**Согласие с модельным черновиком: 11/20 = 55%; покрытие оцененных случаев:
20/21 = 95,24%. Точность относительно проверенного человеком CP-эталона: N/A.**
Один размеченный случай не получил однозначного уровня. Безопасные контроли не
получают приоритет уязвимости. Исходные отсутствующие/partial CP не заменены.

Формула завышает одинаковый компонентный приоритет: почти все backend-находки
получают HIGH, хотя независимый черновик различает ущерб конкретных случаев.
Формула не подстраивалась под этот черновик. Требуется человеческая проверка
референса и последующее отдельное улучшение учета impact конкретной находки.

Результат: `artifacts/public-commerce-cp-validated-2026-10-16/`.
Офлайн-повторение (нужны сохраненный run и закрепленный checkout):

```bash
python -m app.public_commerce_priority \
  --run artifacts/single-pass-search-and-repair-2026-10-16/search \
  --checkout artifacts/benchmark-target/juice-shop \
  --reference artifacts/public-commerce-cp-validated-2026-10-16/reference.json \
  --output artifacts/public-commerce-cp-NEW
```

## Что требуется для закрытия CP

Сценарий уже зафиксирован пользователем. Человеческий рецензент, не сверяющийся
с CP агента, просматривает source/HTTP anchors и независимо указывает LOW/MEDIUM/HIGH
с объяснением и фактами. Для неподходящих или неизвестных случаев сохраняется null
с причиной. Затем отдельно задаются обоснованные архитектурные входы агентному
расчету и сравниваются результаты, с покрытием обоих наборов.

Проверка «эталон = результат той же scoring-функции» не измеряет точность CP.
Утверждать, что независимая разметка уже выполнена человеком, здесь нельзя.
Новый полный поисковый прогон для последующего сравнения не нужен.

## Воспроизведение

```bash
python -m app.scoring_audit \
  --run artifacts/single-pass-search-and-repair-2026-10-16/search \
  --checkout artifacts/benchmark-target/juice-shop \
  --output artifacts/scoring-audit-NEW
```

В новом output сохраняются derivative rescore, runtime impact assessments,
blind reference draft, архитектурный preview, summary и seal. Старые артефакты
не переписываются. CLI не принимает model-generated operator reviews, не
вызывает Executor и не меняет target или замороженные labels.

Результат этого выполнения: `artifacts/scoring-audit-complete-2026-10-16/`.
Precision подтверждений остается 13/13, Recall 13/27, лабораторное время двух
проверенных исправлений 80,986 с. Изменился учет рейтингов, не результаты поиска.
