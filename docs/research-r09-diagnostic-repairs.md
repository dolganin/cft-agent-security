# Исправления после диагностического R09

## Что было сломано

R09 остановился после 6 вопросов, 42 обращений к модели и 35 действий чтения/поиска.
Четыре локальных отказа при подготовке предложения были ошибочно классифицированы
как `model_failure`. Три последовательных отказа завершили всю кампанию.
Два других исследования остановились на повторном действии. HTTP, браузер и скрипты
в этом запуске не использовались. Это не успешный полный benchmark.

## Реализовано

1. Предварительная проверка предложения возвращает модели объяснение недоступного
   пути/метода или повторного действия. Исполнение не происходит. Разрешены две
   дополнительные попытки по умолчанию, в исходных бюджетах запросов/байтов/времени.
2. Исчерпание этих попыток получает отдельный `proposal_corrections_exhausted`.
   Вопрос сохраняется как failed; кампания не считает его отказом провайдера.
3. Нормализованы отпечатки операций: значения параметров по умолчанию и эквивалентные
   поисковые области не позволяют маскировать повтор. Увеличение max_matches после
   полного поиска не считается новым действием. После усеченного поиска увеличение
   лимита допустимо.
4. Только в исследовательском режиме доступны HTML/Pug/HBS/EJS/Vue/Svelte,
   CSS/SCSS и выбранные JSON-манифесты. Индекс ограничен 1024 файлами и 12 MiB.
   На закрепленном checkout Juice Shop: 463 файла вместо 256, доступен ранее
   недоступный administration.component.html и 5 файлов views/.
5. Модель получает первую страницу индекса и явное указание на пагинацию.
   В компактной истории сохраняются пути/параметры и отпечатки прошлых действий.
6. Между вопросами передаются ограниченные сведения о прочитанных участках,
   известных кандидатах, предыдущих интерпретациях и пробелах. Это навигация,
   а не Evidence: для новых claims нужны чтения текущей сессии.
7. Очередь сохраняет чередование источников, но предпочитает серверные обработчики,
   известные точки входа и доступные пути зарегистрированной проверки.
   Эталонные метки при этом не используются.
8. Промпт устраняет противоречие о браузере, просит проверять предположения о
   библиотеках и выбирать эксперимент под конкретный недостающий факт.
9. Добавлен handoff с точным source/route binding для существующих проверок.
   Опциональный мост выполняет старые SQL/directory протоколы через прежние
   Validator, Executor, audit и Evidence. В обновленном диагностическом runner
   он включен с targets/juice-verification.yaml и закрепленным Python worker.
10. Протокол не получает дополнительных HTTP-разрешений из своего профиля:
    POST при read-only scope остается недоступен. Образ/контейнер/сеть и source
    binding проверяются, неподтвержденная очистка останавливает кампанию.
11. Независимый терминальный FinalReport заменяет основной отчет только при
    достаточном Evidence; исходный research_report сохраняется отдельно.
12. Сетевые резервации протоколов учитываются в общем лимите, но не выдаются
    за число фактически наблюдавшихся исследовательских запросов.

## Артефакты новой кампании

- `manifest.json`: индекс, исключения, бюджеты, операторские профили и worker image.
- `questions/*/progress.json`: `proposal_feedback`, модельные шаги, фактический ledger.
- `question-failures.json`: локально исчерпанные предложения, отдельно от провайдера.
- `model-failures.json`: действительные ошибки модельного контракта/провайдера.
- `canonical-verification-handoff.json`: кандидаты и binding, сам по себе не Evidence.
- `canonical-runtime-reviews.json`, `canonical-verification/*/`: реальные фиксированные
  проверки, approval, execution, audit, Evidence и FinalReport.
- `verification-backlog.json`: случаи без достаточного независимого доказательства.
- `summary.json`: запросы исследования, резервации протоколов, расход общего
  сетевого бюджета и раздельные счетчики source/runtime reviews.

## Проверки

Новые регрессии: `tests/test_research_diagnostic_repairs.py`.

Проверяется восстановление после недоступного файла/каталога/метода, повторов,
исчерпание локальных попыток без provider circuit breaker, сохранение бюджетов,
исторический индекс, исключения секретов/оракулов, приоритет очереди и handoff.

Docker-тест проходит настоящий граф: недоступный путь → чтение HTML → повтор →
честное завершение. Выполняется только одно действие и не возникает confirmed.

Отдельный Docker-тест на закрепленном Juice Shop запускает существующую SQL-проверку
как отдельно, так и из исследовательской кампании. Проверяются confirmed с Evidence,
audit, итоговый отчет, сохранение исходного inconclusive и сетевой бюджет 4.
Это тест двойником модели: он проверяет интеграцию, а не качество Qwen.

```bash
python -m pytest -q
python -m ruff check .
python -m app.main

CFT_RESEARCH_IMAGE=<immutable-research-image> \
CFT_RESEARCH_BRIDGE_TARGET=<pinned-juice-checkout> \
python -m pytest -q tests/test_research_diagnostic_repairs.py
```

## Что еще не закрыто

- Приватные пользовательские роли B04/B05 и двухгенерационный B06 пока не
  подключены к этому новому мосту. Нельзя представлять его как поддержку всех B-проверок.
- Браузер по-прежнему начинает отдельную анонимную сессию на действие.
- Увеличение качества поиска живой Qwen после изменений еще не измерено.
- Нет новых Precision/Recall/FPR, трех повторов или MTTR. Старый R09 не переписан.
- Handoff не является автоматическим исполнением неподдержанного протокола.

Следующий инженерный блок — private fixture adapters для B05/B06 с отдельной
регистрацией разрешений, контролями, общим учетом запросов и приемкой. Затем один
живой диагностический запуск без изменения замороженного эталона.

## Итог сохраненных проверок

Полный набор с включенными research Docker-тестами: **1310 passed, 18 skipped**.
Пропуски относятся к отдельным SberLab/AutoDealer, stage1/stage2, A05 demo artifacts
и Docker boundary тестам, требующим других операторских настроек. Ruff, app.main
и git diff --check прошли.

Сохранены оба живых диагностических запуска, не как повторения benchmark:

- `r09-repairs-live-smoke-2026-10-15`: 2 вопроса, 8 обращений к модели,
  4 действия, 0 HTTP. Degraded: ошибка схемы URL и отсутствие alias для настоящего
  Semgrep SQL rule. Запуск сохранен без изменений; проводился до финальных alias/URL
  исправлений. Полный побайтовый снимок этой промежуточной реализации не сохранен.
- `r09-repairs-live-smoke-2026-10-15-v2`: 2 вопроса, 8 обращений к Qwen,
  6 действий, 2 исследовательских HTTP-запроса, 4 зарезервированных запроса
  независимой SQL-проверки. Одно runtime confirmed, второй случай pending.
  Нет model/question failures, degraded=false, cleanup_verified=true.
  Кампания заняла 47.93 секунды и завершилась по лимиту двух вопросов.

В v2 сохранены SHA256 файлов реализации и признак dirty checkout. Это короткая
проверка интеграции с живой моделью, не новые Precision/Recall или воспроизводимость.
Оригинальные исторические результаты и замороженный эталон не изменены.
