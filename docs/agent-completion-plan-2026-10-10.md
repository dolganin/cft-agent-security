## 1. Назначение и правила работы с документом

Цель работы: довести агента до законченного сценария на Juice Shop и подготовить проверяемую оценку для Сергея Беспалова. Приоритеты: качество поиска, надежность подтверждения, самостоятельная подготовка проверенных исправлений и честные метрики. Подготовка презентации Catalyst больше не определяет порядок разработки.

Этот документ задает текущий порядок работ. Планы от 8 октября и прежний roadmap из пяти этапов сохраняются как история решений. Границы безопасности и каноническая архитектура остаются в [AGENTS.md](../AGENTS.md). Если реализация изменит контракт или архитектурную связь, соответствующая документация и схемы обновляются в той же работе.

Как пользоваться:

1. Брать следующий доступный пакет работ из раздела 5.
2. Перед началом прочитать его зависимости, затрагиваемые файлы и критерии готовности.
3. Обновить статус в разделе 20 и записать исполнителя. Предложенное распределение не означает, что коллега уже взял задачу.
4. Выполнить задачи и проверки, сохранить доказательства результата.
5. Отмечать пакет завершенным только при выполнении его приемки. Код, тесты и реальный прогон являются разными видами подтверждения.
6. При изменении объема или протокола измерений записывать решение в раздел 21. Не менять критерии после просмотра итоговых результатов ради улучшения цифр.

Для каждого рабочего пакета обязательны: commit, список проверок с результатами, оставшиеся ограничения, ссылки на артефакты и следующий доступный пакет. Логи и данные запусков хранятся отдельно от Git; в Git входят код, протокол, разметка без секретов и итоговая сводка.

## 2. Законченный сценарий, который строим

Оператор подключает репозиторий и разрешенное тестовое окружение. Он задает границы доступа, тестовые роли и бюджеты, но не перечисляет агенту уязвимости, номера строк или правильные исправления.

Агент:

1. Проверяет готовность окружения, фиксирует исходный commit и конфигурацию.
2. Определяет структуру приложения, маршруты, обработчики, доступные тестовые роли и источники данных.
3. Выполняет SAST, изучает релевантные исходники и формирует собственные кандидаты.
4. Объединяет дубли, сохраняя происхождение, и связывает кандидатов с разрешенными способами проверки.
5. Предлагает проверку; Validator разрешает ее; Executor выполняет в изоляции.
6. Формирует вывод из сохраненных доказательств. При нехватке информации объясняет конкретную причину.
7. Оценивает техническую серьезность и контекстный приоритет отдельно.
8. Для подходящей подтвержденной находки генерирует патч и регрессионный тест.
9. В одноразовой копии воспроизводит проблему до патча, применяет патч, выполняет сборку, функциональные и независимые security-проверки после патча.
10. При неудаче разбирает результат и делает ограниченное число новых попыток.
11. Отдает проверенный diff, тесты, доказательства и временные показатели; при разрешенной интеграции готовит PR.
12. Позволяет повторить тот же эксперимент и пересчитать метрики из сохраненных артефактов.

```text
Репозиторий + операторский профиль + тестовое окружение
                         |
             Discovery / SAST / Scout
                         |
                Очередь кандидатов
                         |
           Reasoning -> Validator -> Executor
                ^                       |
                +------- Evidence ------+
                         |
              FinalReport + исходный Gate
                         |
              подтвержденная находка
                         |
          LLM patch -> review -> isolated verify
                         |             |
                    новая попытка <----+ при допустимой неудаче
                         |
            verified patch + fix artifact
                         |
             ревью / PR / CI / применение

Внешний evaluator читает результаты поиска, проверки и исправлений.
Эталонные ответы не передаются производственному агенту.
```

Ожидаемый первый дополнительный сквозной случай: агент обнаруживает ошибку владения корзиной, подтверждает ее на двух тестовых пользователях, сам предлагает исправление, сохраняет доступ владельца и блокирует доступ другого пользователя. SQL-сценарий остается регрессионной опорой.

### 3.2. Ограничения, подтвержденные текущим кодом

- `benchmarks/juice-shop-v20.2.0/benchmark.yaml` выбирает демонстрационные правила из `docs/demo/semgrep.yaml`: два правила с явными ограничениями по файлам.
- Этот профиль ограничивает Scout двумя ходами и четырьмя кандидатами; на находку разрешены две итерации. Это параметры конкретного бенчмарка, а не предел возможностей всего кода.
- `sast/normalizer.py` переносит путь сканера в `Finding` без общей канонизации; `discovery/scout.py` и `agent/verification.py` используют точное сравнение строк путей.
- Runtime-привязки в `targets/juice-presentation.yaml` зависят от файла и начальной строки находки. Сдвиг или другой якорь может лишить находку применимой проверки.
- Основные новые runtime-возможности Juice Shop относятся к SQL и перечислению чувствительных имен файлов. Другие категории не имеют сопоставимой законченной проверки.
- `app/stage1_e2e.py` без готового review использует `IntegrationPatchClient`, который формирует заранее заданное SQL-исправление. Это проверяет verifier, но не самостоятельное исправление моделью.
- `scoring/service.py` возвращает `UNASSESSED` для обычных CVSS-находок. Context Priority вычисляется, но его точность относительно независимой разметки пока не измерена.
- Текущий benchmark-контракт требует source-файл и строку; для полноценного сравнения с DAST нужен отдельный способ сопоставления HTTP-наблюдений.

### 3.3. Что известно только из опубликованного отчета

[Отчет Stage 2](stage2-benchmark-report.md) описывает три прогона: 5 из 10 эталонных положительных случаев обнаружены, 3/2/2 подтверждены, среднее время около 491 секунды. Scout просмотрел примерно 3–4% проиндексированных строк; прирост recall на этом эталоне равен нулю. Отчет отмечает несовпадения Windows-путей и runtime-привязок.

[Отчет Stage 1](stage1-fix-verification-report.md) описывает успешные Docker-повторы исправления SQL-сценария.

Эти отчеты не заменяют локального воспроизведения. На момент последней проверки в этом чате исходные артефакты коллеги отсутствовали локально, Docker daemon был недоступен. В пакете W0 это состояние нужно проверить заново. Нельзя объяснять все неудачи одной причиной без повторного воспроизведения.

Локальная проверка после обновления до `22aab5d`: 495 backend-тестов прошли, 18 пропущены; 28 frontend-тестов прошли; сборка, Ruff и `app.main` прошли. Это исторический результат проверки в этом чате, а не вечное требование к количеству тестов.

## 4. Объем, приоритеты и неизменяемые ограничения

### 4.1. Обязательный объем завершенного этапа

- Juice Shop зафиксированной версии как основной реальный target.
- Стабильная работа существующих SQL/file-exposure проверок.
- Полноценный режим поиска, отдельный от короткого demo.
- Законченные проверки ownership/access control, authentication и open redirect; отдельная ограниченная проверка code injection для существующего эталона.
- Самостоятельная генерация и проверка исправлений как минимум в трех семействах, если их пригодность подтверждена заранее.
- Измерение всех запрошенных Беспаловым показателей либо явное указание отсутствующих данных с причиной.
- Воспроизводимая передача: запуск, результаты, объяснение ограничений, возможность пересчета метрик.
- Один пользовательский путь от проекта к находке, доказательству и исправлению.

### 4.2. Что не входит в критический путь

Косметическая переработка UI, презентационные страницы, многоагентность, Kubernetes, новая векторная база, большой каталог сканеров, универсальная поддержка всех языков, production-проверки. XSS и traversal можно добавлять после основных измеренных пробелов; для новых категорий нужна новая версия эталона.

Автоматизация PR идет после работоспособной генерации и проверки патчей. Доставляемый patch bundle допустим до нее и уже позволяет оценивать качество исправлений.

### 4.3. Границы архитектуры

- Любая активная проверка проходит существующий Validator и зарегистрированный Executor.
- LLM не выбирает произвольный target, host path, секреты или сетевую область.
- `sandbox_command` остается разрешенной общей возможностью внутри существующей networkless Docker-границы. План не отменяет ее, но ее stdout сам по себе не дает подтверждение уязвимости.
- Модельные команды и код target не выполняются на хосте. Fixed Git/data operations для создания snapshot и применения diff остаются ограниченными операциями сервиса.
- Runtime-маршруты, тестовые роли и разрешенные классы действий определяются оператором. Discovery может предлагать новые маршруты, но не выдавать себе разрешение на них.
- Исходный checkout, исходный `FinalReport` и Gate не перезаписываются результатом исправления. У исправления отдельный артефакт и проверка нового commit.
- Ни эталонные ответы, ни готовые эталонные патчи, ни скрытые приемочные тесты не попадают в контекст модели.
- Сохраняются лимиты времени, действий, вывода, ресурсов и числа попыток; ошибки очистки не скрываются.

## 6. W0 — воспроизвести исходную точку

Цель: отделить ошибки инфраструктуры, платформы, конфигурации и агента до внесения улучшений.

Файлы: `app/config.py`, `app/stage1_e2e.py`, `app/stage2_benchmark.py`, `evaluation/benchmark_harness.py`, `docs/demo/README.md`.

### Задачи

- [ ] **W0.1. Инвентаризация.** Зафиксировать agent commit, target commit, ОС/архитектуру, Python/Node/Docker/Semgrep, фактически доступную модель и все влияющие настройки без значений секретов.
- [ ] **W0.2. Provisioning.** Подготовить отдельные чистые target checkout для benchmark и fix verification. Проверить исходные bytes/LF, image digests, изоляцию сетей и ресурсы.
- [ ] **W0.3. Образы.** Проверить, что документированная сборка fix image дает идентификатор, принимаемый `pinned_image`. Локальный tag после `docker build` может не иметь `RepoDigests`; если инструкция не воспроизводится, исправить provisioning и pinning, сохранив проверку неизменяемого образа и `--pull never` во время эксперимента.
- [ ] **W0.4. Preflight.** Отдельно проверить Docker, target health, сканер, доступность модели и возможность сохранения артефактов. Нейтральный LLM-probe не считать анализом проекта.
- [ ] **W0.5. Baseline replay.** В новом каталоге выполнить один полный прогон текущего v1 и отдельно Stage 1. Сохранить все неудачи и причины. Условия запущенного эксперимента не менять посередине.
- [ ] **W0.6. Root-cause ledger.** Для каждого незавершенного SQL/file-case записать цепочку: raw finding → normalized finding → candidates → выбранное действие → Validator → execution → Evidence → final verdict.
- [ ] **W0.7. Переносимость.** Проверить данные Windows-путей в unit/integration fixtures на любой платформе; минимум один реальный запуск на каждой платформе, для которой заявляется поддержка. Если Windows-run недоступен, явно ограничить платформенное обещание.

### Приемка W0

Есть пакет воспроизведения и таблица причин по каждому неуспеху. Отсутствие Docker, неверный ключ, несовместимый image, timeout и ошибка интерпретатора различаются. Baseline хранится неизменным и имеет отдельный run ID. Если воспроизведение заблокировано, статус остается `blocked` с конкретным prerequisite; можно продолжать независимые кодовые задачи, но baseline не объявляется полученным.

### W1.4. Два способа сопоставления с эталоном

- [ ] Source-наблюдения: canonical artifact + семейство + service + разрешенный anchor/range.
- [ ] DAST-наблюдения: service + HTTP method + route template + parameter/location + семейство + контекст authentication + требуемые observations.

- [ ] Алиасы caller/helper и альтернативные source anchors задаются по исходникам до итоговых прогонов. Совпадения по похожему тексту или одному CWE недостаточно.

### W1.5. Семантика показателей

Основная единица качества — distinct case внутри одного запуска. Нельзя считать повторные наблюдения одной уязвимости независимыми случаями.

Обозначения: `P` — число положительных эталонных случаев; `N` — число отрицательных; `TPc` — положительные случаи с подтверждением, поддержанным Evidence; `FPc` — отрицательные случаи с таким подтверждением; `TNexplicit` — отрицательные случаи с обоснованным `rejected`.

| Показатель | Формула / правило | Обязательная оговорка |
|---|---|---|
| Precision по запросу Беспалова | `TPc / (TPc + FPc)` | Среди сопоставленных подтверждений; отдельно число неподдержанных claims и неразмеченных подтверждений |
| Verified Recall по запросу Беспалова | `TPc / P` | Пропущенные, inconclusive, blocked и ошибочные случаи не дают TP |
| False positive rate | `FPc / N` | Это доля отрицательных контролей с ложным подтверждением; отсутствие проверки не равно доказанному `rejected` |
| Доля ложных среди confirmed | `FPc / (TPc + FPc)` | Это `1 - precision`, а не FPR |
| Detection recall | `detected_positive_cases / P` | Дополнительный показатель поиска, не подмена verified recall |
| Detection precision/F1 | По исходным кандидатам и отдельной detection confusion matrix | Сканерный alert не приравнивается к agent confirmed |
| Полнота решения | `(TPc + FPc + explicit_positive_rejections + TNexplicit) / (P + N)` | Показывать раздельно уверенные и неуверенные/непроверенные исходы |
| Точность вердикта на всем наборе | `(TPc + TNexplicit) / (P + N)` | Abstention и отсутствие находки не дают правильного отрицательного вердикта |
| Точность среди решенных | Правильные explicit verdicts / все explicit verdicts | Только вместе с полнотой решения |
| Severity accuracy | Совпавшие severity / все заранее применимые размеченные случаи | Неоцененные/пропущенные случаи считаются неуспехом в end-to-end срезе |
| Severity accuracy на оцененных | Совпавшие / выданные применимые оценки; дополнительно vector agreement и MAE численного score | Показывать coverage оценки; не смешивать с end-to-end accuracy |
| Context Priority accuracy | Совпавшие уровни / заранее размеченные применимые случаи | Дополнительно coverage и accuracy на оцененных; rubric проекта, не универсальный стандарт Juice Shop |
| Воспроизводимость | Частота detection/confirmed по case, совпадение verdict, разброс времени, Jaccard кандидатов | Считать одинаковые конфигурации; 3 повтора не дают доказательства абсолютной стабильности |
| Техническая надежность | Доля технически неуспешных запусков и отдельных workflow | Отдельно provider fallback, timeout, policy block и отсутствие capability |

`explicit_positive_rejections` в формуле полноты решения — положительные случаи, ошибочно получившие `rejected`: это решенные, но неверные случаи. Для прозрачности сохранять матрицу `expected × observed` с колонками confirmed/rejected/inconclusive/policy_blocked/technical_error/not_detected.

Дополнительные правила:

- [ ] Знаменатель 0 дает `N/A`, не 0% и не 100%.
- [ ] Всегда показывать числитель/знаменатель рядом с процентом.
- [ ] Для долей добавить интервалы неопределенности с указанным методом; не считать одинаковые случаи в повторных runs новой независимой выборкой. Разброс по запускам показывать отдельно.
- [ ] Unsupported `confirmed` не считать правильным ответом; публиковать отдельный критический счетчик и отправлять на расследование.
- [ ] Для неразмеченных confirmed нельзя заявлять полную precision проекта. Нужна независимая проверка этих находок или условная формулировка результата.
- [ ] В safe-case tests принудительная подача кейса verifier измеряет качество verifier отдельно. Она не засчитывается как самостоятельный поиск агента.
- [ ] Preflight-blocked попытки не считать all-FN; учитывать их в журнале запусков. Ошибки после старта не удалять. Публиковать качество на completed runs вместе с completion rate и операционным срезом всех начатых попыток.

### Приемка W1

Есть versioned protocol, source/runtime-grounded dataset, development/holdout split, frozen matching, формулы, schema validation и тесты на дубли, abstention, неизвестные находки и нулевые знаменатели. Ни одна итоговая метрика не требует ручного исправления JSON после запуска.

XSS/traversal — следующая очередь после W4.6–W4.10. Интеграция готового движка допускается после проверки его воспроизводимости, лицензии, изоляции и полезности на выбранных случаях. Один инструмент не равен готовой capability.

### W7.4. Независимая проверка исправления

Обязательная цепочка для `security_verified=true`:

1. На исходной версии воспроизведена именно исходная уязвимость.
2. Proposal прошел строгий review и применен только к snapshot.
3. Сборка и обязательные исходные тесты прошли.
4. Добавленный регрессионный тест проверен на исходной и исправленной версии, когда это применимо.
5. Точная исходная security-проверка после патча дала обоснованное отрицательное подтверждение.
6. Независимые заранее заданные варианты проверки не воспроизводят исходную причину.
7. Сохранено нормальное поведение: доступ владельца, поиск, допустимая смена пароля или разрешенный redirect.
8. Исходный checkout не изменился, область diff соблюдена, cleanup завершен.

- [ ] Набор обязательных независимых checks определяется до генерации патча. Модель не может пометить неудобный check необязательным.
- [ ] Для model-generated tests фиксировать, почему они падают до патча. Ошибка импорта/сборки теста сама по себе не является RED-воспроизведением уязвимости.
- [ ] Не принимать отключение маршрута, всегда пустой ответ, запрет доступа всем пользователям или удаление теста как исправление при нарушении функционального контракта.
- [ ] Добавленные моделью тесты выполняются только внутри изолированного adapter и не заменяют независимый verifier.
- [ ] Известные upstream flaky/skip фиксируются до опыта. Новые падения после патча не объявляются flaky без воспроизведения и расследования.
- [ ] Успешное исправление означает устранение проверенной причины в заявленном scope, а не отсутствие всех возможных уязвимостей проекта.

### W7.5. Ограниченный цикл повторных попыток

- [ ] Начальный development default: не более трех предложений на случай. Общий wall-clock budget выбрать по W0/W7 измерениям и заморозить до оценки; последующие настройки создают новый experiment.
- [ ] Возвращать модели конкретные безопасные diagnostics: diff rejected, build error, failing functional test, original probe still confirms, insufficient evidence.
- [ ] Каждую попытку применять к новой копии исходного commit. Накопление патчей возможно только как явно проверенный combined diff, привязанный к тому же base.
- [ ] Не повторять одинаковый proposal digest или одинаковую безрезультатную стратегию без новой информации.
- [ ] Timeout, cancellation, model unavailable, exhausted attempts, cleanup failure дают отдельный terminal reason и сохраняют историю.
- [ ] Автоматический повтор после provider error использует оставшийся общий бюджет и учитывается во времени; ошибка авторизации не запускает бесконечную очередь.

### W7.6. Данные и метрики исправлений

Зафиксировать множество `C` — distinct истинно подтвержденные случаи; `E` — eligible случаи по заранее объявленной политике; `F` — случаи с проверенным исправлением; `A` — все попытки применения патча; `R` — случаи/попытки с доказанной регрессией. Каждое множество публикуется вместе с причинами исключения.

| Показатель | Определение |
|---|---|
| Fix eligibility coverage | `E / C` |
| Verified fix rate на eligible | `F / E`; не начатая из-за бюджета или ошибочная попытка не исчезает из знаменателя |
| End-to-end remediation recall | Самостоятельно найденные, подтвержденные и исправленные случаи / все заранее объявленные положительные случаи |
| First-attempt success | Eligible случаи с verified fix на первой попытке / `E` |
| Pass within budget | Успех за заданное число attempts и общий лимит времени / `E` |
| Regression rate | Отдельно число eligible cases с хотя бы одной регрессией / `E` и число regressive applied attempts / `A` |
| Human acceptance | Принятые человеком предложения / реально рассмотренные человеком; неизвестно без ревью |
| Attempts | Распределение числа попыток, включая неуспешные случаи |
| Verified-fix latency | Время от доступного confirmed finding до первого verified patch; очередь, генерация, review, build и все попытки включены |
| End-to-end latency | От начала анализа до verified patch; отдельно от fix-only latency |

### W7.7. MTTR и временные события

Добавить append-only события: `run_started`, `finding_observed`, `finding_confirmed`, `fix_eligibility_decided`, `fix_queued`, `attempt_started`, `proposal_ready`, `verification_finished`, `fix_verified`, `review_accepted`, `fix_merged`, `fix_deployed`, `remediation_validated`.

У события: run/finding/fix/attempt ID, UTC timestamp, монотонная duration внутри процесса, commit/digest, actor и причина. Повтор события не должен удваивать статистику. Токены/секреты в events не включаются.

Для этого проекта договориться о следующих определениях:

- **Автоматическое время до проверенного патча:** `fix_verified - finding_confirmed`. Это наш основной лабораторный показатель скорости исправления.
- **Время до merge:** `fix_merged - finding_confirmed`. Это процесс разработки, не доказательство исправления в развернутой среде.
- **Фактическое время устранения:** `remediation_validated - finding_confirmed`, где `remediation_validated` означает проверку исправленной версии в согласованной целевой среде. Среднее этого времени можно назвать MTTR с явно указанным определением.
- Исторический MTTR остается N/A: реальных записей обнаружения и устранения нет. Нельзя восстановить их из длительности Stage 1.
- Для будущих лабораторных запусков можно измерять примененную и перепроверенную sandbox-remediation отдельно, явно назвав ее лабораторной, без приравнивания к production MTTR.
- Для неуспешных/незавершенных случаев сохранять длительность наблюдения и terminal reason. Среднее только успешных случаев всегда сопровождать success rate, числом незавершенных и лимитом наблюдения.
- Публиковать mean/median, диапазон и p90 при достаточном числе случаев; для маленькой выборки показывать все индивидуальные времена и не преувеличивать значение перцентилей.

### Приемка W7

Проведены реальные LLM fix attempts на заранее размеченном наборе минимум из шести пригодных distinct cases не менее чем трех семейств; минимум часть случаев не использовалась при настройке генерации. Если набор такого размера еще не подготовлен, пакет не объявляется общим benchmark исправлений.

Есть успешные и неуспешные истории, исходные/исправленные digests, независимые checks, статистика попыток и времени. Для первых заявленных семейств получены настоящие model-generated verified fixes. Заранее написанный SQL-патч фигурирует только в regression-срезе verifier.

- [ ] Передаваемый архив без `.env`, credentials, `.venv`, `node_modules`, Docker layers и нерелевантных пользовательских файлов. Большие raw artifacts передавать отдельным пакетом с manifest; не выдавать один Markdown за полный evidence bundle.

## 16. Критерии приемки продукта и критерии качества

Техническая готовность и качество модели оцениваются отдельно. Возможна ситуация, когда программа работает правильно, но recall недостаточен: в таком случае исследовательский результат сохраняется, а цель улучшения остается незавершенной.

### 16.1. Обязательные инженерные критерии

- [ ] Все активные действия проходят Validator; новые bypass отсутствуют.
- [ ] Нет неподдержанных `confirmed` и `security_verified=true` в приемочных случаях.
- [ ] Положительный и отрицательный контроль проходят для каждой заявленной capability.
- [ ] Штатный CI-проход использует доступные инструменты без ручной подстановки finding IDs/строк.
- [ ] Тесты текущего проекта и целевого приложения разделены; opt-in skips объяснены.
- [ ] История ошибок, attempts, fallback, partial coverage и cleanup сохранена.
- [ ] Самостоятельная генерация патча измерена отдельно от verifier с готовым патчем.
- [ ] Метрики пересчитываются из артефактов; все знаменатели и scope определены.
- [ ] Пользователь может получить отчет и patch bundle через законченный путь.

### 16.2. Предварительные внутренние цели качества

Это предлагаемые цели разработки, не обещанные результаты и не требования, уже согласованные с Беспаловым. Их нужно закрепить в W1 до настройки v2. Если размер/состав корпуса меняется, цели рассматриваются до новых итоговых запусков.

| Область | Рабочая цель |
|---|---|
| Старый development v1 | Detection не менее 8/10 и evidence-confirmed не менее 7/10 при заявленном полном профиле; сравнить с воспроизведенным baseline |
| Расширенный holdout | Verified recall не менее 70%, confirmed precision не менее 90%, FPR не более 5% на размеченных контролях; обязательно интервалы и размеры выборки |
| Дополнительная польза | Измеримый прирост хотя бы по заранее выбранной основной цели: verified recall при сопоставимом бюджете или время/объем ручной проверки при сопоставимом качестве |
| Исправления | Verified fix rate не менее 60% на заранее определенном eligible наборе; минимум три семейства и шесть distinct eligible cases |
| Регрессии | Ноль незамеченных verifier регрессий в принятых `FIXED`; все неудачные attempts отражены в regression rate |
| Операционная надежность | Все запланированные итоговые runs учтены; технические отказы расследованы. Три успешных повтора не называются доказательством 100% надежности |
| Скорость | До W1 freeze установить целевой wall-clock budget по измерению W0; публиковать tradeoff времени и качества, не ускоряться скрытым урезанием объема |

Нулевой FPR на маленьком наборе не доказывает безопасность на произвольном проекте. Выполнение численных целей на известных development cases не заменяет holdout и переносимость.

Если цель не достигнута, фиксируется результат и причина. Нельзя менять matching, исключать трудные случаи или увеличивать бюджет только неудачных итоговых runs без создания отдельного эксперимента.

## 17. Проверки, которые должны сопровождать изменения

## 18. Артефакты и защита от потери результатов

Предлагаемая структура будущего эксперимента; часть файлов требует реализации в W1/W7/W9:

```text
artifacts/experiments/<experiment-id>/
  protocol.json
  configuration.json
  dataset-lock.json
  environment.json
  attempts.jsonl
  runs/<run-id>/
    manifest.json
    pipeline/                 # существующие canonical artifacts
    coverage.json
    measurements.json
    case-results.json
    fixes/<fix-id>/
      eligibility.json
      events.jsonl
      attempts/<attempt-id>/
        proposal.patch
        review.json
        before/
        after/
        verification.json
      result.json
    seal.json
  scorecard.json
  scorecard.md
  checksums.sha256
  limitations.md
```

Требования:

- Сохранение результата после каждой завершенной фазы/попытки, атомарная запись итоговых JSON.
- Большие raw logs отдельно; UI/API не раскрывают локальные пути или секреты.
- Проверка digest при пересчете; измененный sealed run исключается с явной причиной.
- Резервная копия итогового evidence bundle в согласованное хранилище; проверка восстановления до отправки отчета.
- `--resume` на уровне run не считать восстановлением незавершенной внутренней фазы. Внутренние checkpoints вводить только с проверкой commit/config/session и безопасным восстановлением окружения.
- После сбоя не повторять необратимую операцию в той же сессии без проверки состояния. Для лабораторного исправления безопаснее новая копия и новая попытка с общей историей.

Рабочие правила:

- Ветка по конкретной задаче от актуального `main`, например `codex/finding-path-bindings` или принятый командой `feature/...`.

- Стадировать только нужные файлы. Не включать `.env`, environments, caches, target checkouts и unrelated projects.
- PR содержит проблему, изменение поведения, затронутые shared contracts, тесты и ограничения.
- Merge после обязательных проверок и review. Публикация включает push и проверку remote hash, когда это входит в поручение.
- Удаление отслеживаемого bytecode и устаревших legacy fix models выполнять отдельной механической задачей после проверки потребителей. Не смешивать такую очистку с изменением security semantics.
- Старые результаты не удалять: помечать их scope и исторический статус. `demo` остается полезным smoke-профилем.
