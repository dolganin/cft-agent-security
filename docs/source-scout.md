# Поиск кандидатов по исходному коду

B03 добавляет opt-in режим `handlers`, приоритетные окна, bounded import follow-up
и явные непросмотренные диапазоны. Старый `round_robin` остается по умолчанию.
Включение, сравнение с SAST и ограничения: [B03](b03-source-exploration.md).

S02: SAST и Scout используют общий нормализатор путей и source identity.
Объединяются только однозначные одинаковые диапазоны одного семейства и сервиса
в одном файле/версии, а не любое пересечение строк. Все источники, описания,
source IDs и rationale сохраняются в `Finding.provenance.observations`.
Разные scanner columns разделяют дефекты на одной строке; кандидат без columns
не выбирает один из нескольких sinks. Подробности: [контракт S02](s02-finding-normalization.md).

RepositoryScout читает исходники из доверенного Discovery inventory и передает
модели пронумерованные окна кода. Сначала просматриваются файлы с обработчиками
запросов, операциями SQL, проверками прав, выводом HTML и доступом к файлам.
Это эвристика порядка чтения, а не детектор или доказательство уязвимости.

Модель может запросить дополнительные окна файлов и поиск буквальной строки
(например, имени функции). Приложение выполняет только ограниченное чтение
из заранее построенного корпуса. Относительные импорты подсказывают связанные
файлы. Команды, URL и пути вне корпуса этот интерфейс не принимает.
Для JavaScript/TypeScript строится ограниченный список прямых Express route
registrations и предшествующих `app.use` в том же файле. Он связывается с
импортированными handler-файлами, сохраняется как
`scout/express-source-map.json` и передается модели только для текущего кода.
Для принятых кандидатов рядом сохраняется `candidate-route-links.json` с точными
source anchors, совпавшими route ID и основанием связи. При нескольких маршрутах
связь отмечается неоднозначной; авторизация всегда остается `unknown`, пока
отдельная проверка не предоставит доказательство.
Это инвентарь регистраций, а не доказательство того, что middleware разрешает
или блокирует доступ. Динамические маршруты остаются неизвестными. Карта
распознает прямые вызовы `app/router.get|post|put|patch|delete|head|options|all`
и `use` с однозначными статическими путями. Цепочки `app.route(...).get(...)`,
вычисляемые псевдонимы Router и сложные динамические mount-префиксы могут быть
не распознаны; неизвестность не трактуется как отсутствие защиты. Имена и порядок
middleware показывают только регистрацию и не подтверждают корректность проверки.

Поддерживаются JS, TS, JSX, TSX, MJS, CJS и Python. Из корпуса исключены
зависимости, сборки, тестовые каталоги и известные файлы тестов, .env и каталоги
codefixes. Каталоги hacking-instructor, benchmark, ground-truth и solutions также
исключены из чтения Scout, чтобы ответы Juice Shop не попадали в контекст модели.
Тестовые находки SAST продолжают поступать в основной конвейер.
Значения распознаваемых строковых секретов маскируются. Известные комментарии
vuln-code-snippet скрываются с сохранением нумерации строк; это не гарантирует
исключение всех возможных подсказок бенчмарка из произвольного проекта.

Кандидат принимается только с точными прочитанными строками и provenance из
прочитанных файлов. Даже такой кандидат остается гипотезой. Доказательства,
Validator, Executor и окончательный вердикт принадлежат обычному конвейеру.
Модель Scout не задает severity: неподтвержденная оценка серьезности не должна
попадать в CVSS или отчет как измеренный факт.

Кандидаты объединяются с SAST по совпадению файла, пересечению диапазонов и
семейству правила. Разные классы ошибок на одной строке сохраняются. Новые ID
вычисляются из семейства, пути и диапазона, поэтому стабильны при перестановке
ответов модели. Rationale и предложенный способ проверки передаются в Finding.

## Бюджет и наблюдаемость

По умолчанию: 8 ответов модели, до 32 принятых кандидатов, 160000 символов
прочитанных исходников, 240 секунд на исследование. Если следующий уникальный
кандидат упирается в лимит, причина остановки будет `candidate_budget`.
Выполняющийся запрос завершается согласно таймауту транспорта,
поэтому общий срок может превысить этот бюджет на время текущего запроса и
его резервных маршрутов. Корпус ограничен 256 файлами, 4 МиБ суммарно и
128 КиБ на файл. Окно чтения содержит до 160 строк и 10000 символов.
Порядок обхода и ограничения означают, что весь проект может не быть прочитан.
Литеральный поиск ограничен 16 совпадениями суммарно на шаг и учитывается
в бюджете нового исходного текста. Повторный контекст ограничен 12000 символами
на запрос и сохраняет недавно прочитанный код, даже без готовых кандидатов.
Начальные окна обходятся по очереди между файлами, чтобы большой файл не
занимал весь бюджет раньше остальных.

Настройки: CFT_SCOUT_MAX_TURNS, CFT_SCOUT_MAX_CANDIDATES,
CFT_SCOUT_MAX_SOURCE_CHARS и CFT_SCOUT_WALL_CLOCK_SECONDS. В `submitted_ranges` записывается код, отправленный
модели; в `reviewed_ranges` попадает только код из запросов с корректным ответом.
Покрытие и причины остановки записываются в scout/summary.json; кандидаты и
объединенная очередь сохраняются рядом.
Сбой модели сохраняет предыдущие кандидаты и получает model_unavailable.

CI использует Scout после SAST в режиме llm. CLI pipeline самостоятельно
создает Discovery inventory, если оркестратор не передал его.
В интерфейсе этап отображается как «Поиск по исходному коду» и показывает
номер шага, просмотренные файлы, число кандидатов и причину остановки.

Для отдельной проверки только поиска, без запуска целевого приложения:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m app.scout \
  --target /path/to/approved/repository \
  --output-dir artifacts/source-scout \
  --max-output-tokens 4096
```

Такая проверка измеряет работу поиска. Количество кандидатов не является
количеством подтвержденных уязвимостей или измерением recall.

## Изолированный blind-поиск по широкой поверхности

Для диагностического мини-цикла можно исследовать зарегистрированную широкую
часть приложения, не передавая Scout готовые SAST-находки. Сейчас доступны
операторские профили `account-lifecycle` и `catalog-and-reviews`:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m app.scout \
  --target artifacts/benchmark-target/juice-shop \
  --output-dir artifacts/scout-account-mini-01 \
  --blind-discovery --surface account-lifecycle \
  --max-turns 4 --max-source-chars 60000 --wall-clock-seconds 120
```

`--blind-discovery` несовместим с `--sast-findings`: команда завершится до
создания клиента модели. `--surface` ограничивает одновременно исходники,
импортные переходы и карту маршрутов точным allowlist профиля; отсутствующий,
исключённый или неиндексируемый файл отклоняет запуск целиком. Это
`targeted_development_run`, а не измерение общего Recall. Для полного поиска
укажи `--blind-discovery` без `--surface`.

`blind-manifest.json` фиксирует target Git revision (если доступна), хеши
профиля, prompt, карты маршрутов и именно той безопасной проекции исходников,
которую индексирует Scout. Он также явно указывает отсутствие SAST-seed,
benchmark labels, oracle-контроллеров и размеченных vulnerability-регионов.
Манифест не содержит полный текст исходников и сам по себе не означает, что
модель вызвана или что кандидат подтверждён. Вызов модели требует настроенного
провайдера; проверки прав и runtime-доказательство остаются отдельной фазой.
