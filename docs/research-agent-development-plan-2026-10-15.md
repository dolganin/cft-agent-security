# Исследующий security-агент в песочнице: план разработки

Дата: 15 октября 2026. Статус: план, не реализованные возможности.
Основание: код `40f6633`, отчет B09 и решения пользователя в обсуждении.
Новый стек и готовые open-source компоненты разрешены. Приоритет — измеряемое
качество, а не сохранение текущего фреймворка. Этот документ пока не меняет
политики, архитектуру в Miro, полномочия инструментария или статусы карточек.

## 1. Что хотим получить

Агент исследует разрешенный проект и его одноразовый runtime как инженер:
читает связанные файлы, сопоставляет код с поведением приложения, выдвигает
гипотезы, пишет вспомогательные скрипты, выполняет разрешенные эксперименты,
анализирует результат и выбирает следующий шаг. SAST/DAST дают зацепки, но
не ограничивают список вопросов, которые агент способен исследовать.

Результат — воспроизводимый пакет наблюдений и выводов, а не убедительный текст.
Не обещаем 100% обнаружение или отсутствие ложных подтверждений. Качество
проверяем на замороженном эталоне и новых независимых контрольных случаях.

Законченный сценарий:

```text
Проект + операторский scope + конфигурация бюджета
  → инвентаризация кода и работающего приложения
  → SAST / ограниченный DAST / самостоятельное исследование
  → единая очередь гипотез с происхождением
  → выбранный следующий эксперимент
  → Validator → Executor → сохраненные наблюдения
  → переоценка и продолжение исследования
  → независимая проверка заявленного результата
  → FinalReport + CI Gate + архив + отдельный offline-оценщик
```

Модель не знает ответы эталона, не владеет механизмом утверждения permissions
и не может сама превратить свой текст или stdout в trusted Evidence.

## 2. От чего отталкиваемся

В валидном B09: 27 известных уязвимых original случаев и 8 безопасных;
13 уязвимых найдены, 5 подтверждены. 14 не найдены, 8 найдены без подтверждения.
На DEV результат поиска вырос с 1/20 до 10/20; HOLDOUT остался 3/7.
Это выбранный набор, а не весь список challenges Juice Shop.

Что уже полезно и должно сохраниться:

- нормализация Finding, provenance и дедупликация;
- изоляция Docker, Validator, approval binding и source snapshots;
- инструменты SQL/файлового листинга и B06, операторские B04/B05 fixtures;
- сохраненные execution/audit, traces, восстановление B07;
- независимый scorer, эталон A04 и архивы исторических измерений;
- UI/API и контракты FinalReport/Gate, где совместимость разумна.

Установленные ограничения текущего кода:

1. `agent/verification_routing.py` и `app/pipeline_run.py` прекращают работу
   с находкой, если не найден существующий операторский runtime-маршрут.
2. `_requires_registered_candidate` в `agent/llm_model.py` для JavaScript
   artifacts ограничивает модель готовыми кандидатами. Одного изменения
   внешнего маршрутизатора недостаточно: внутренний планировщик тоже нужно менять.
3. `sandbox_command` уже допускает Docker-команды, но скрипты передавать
   через ограниченные argv неудобно; отсутствует полноценный файловый интерфейс.
4. Общие команды имеют network=none. Это нужно сохранить, а HTTP дать через
   отдельную доверенную capability, не открывать произвольную сеть всему shell.
5. Scout просмотрел 15.04% проиндексированных строк и остановился по source budget.
   Это не полный обзор; проценты строк не являются метрикой качества анализа.
6. B05 предлагает только поддержанную own-read проверку; write-v3 не принят.
7. SAST дает много побочных сигналов. DAST в B09 заново не запускался и
   не был живым источником очереди агента.

Не объясняем низкий результат только моделью, бюджетом или фильтрами безопасности:
есть конкретные ограничения orchestration и покрытия инструментов.

## 3. Роли компонентов в новом контуре

| Компонент | Ответственность | Чего не должен делать |
|---|---|---|
| SAST | Быстро искать статические зацепки | Объявлять каждый alert уязвимостью |
| DAST | Исследовать разрешенную HTTP-поверхность, давать runtime-зацепки | Сам расширять scope или менять эталон |
| Агент | Искать, планировать, писать скрипты, переоценивать гипотезы | Сам разрешать действия и удостоверять собственный результат |
| Harness | Управлять контекстом, состоянием, инструментами и бюджетом | Незаметно выполнять SDK-инструменты мимо Validator |
| Validator | Детерминированно разрешать конкретное действие | Использовать benchmark labels как permissions |
| Executor | Выполнять одобренное действие в нужной лаборатории | Исполнять target-код или model scripts на хосте |
| Evidence/reviewer | Проверять наблюдения, controls, происхождение и предел вывода | Принимать строку «confirmed» как доказательство |
| Оценщик | Сопоставлять результат с независимым эталоном | Подсказывать ответы агенту |

Готовые проверки сохраняются как надежные быстрые инструменты, но отсутствие
готовой проверки больше не означает отсутствие разрешенного исследования.

## 4. Выбор стека и переиспользование

### Кандидаты, просмотренные по первичным публичным источникам

| Вариант | Подтвержденные свойства | Что хотим проверить у нас |
|---|---|---|
| Расширение Python/LangGraph | Уже интегрирован с нашим Validator/Executor/Evidence | Можно ли быстро снять ограничения без очередной цепочки одноразовых tools |
| OpenHands Software Agent SDK | Python/TS/REST, инструменты terminal/file editor, disposable workspaces; MIT | Harness для чтения/редактирования/циклов, перехват всех side effects |
| Strix | Заявлены Docker runtime, terminal, Python, HTTP proxy и browser; Apache-2.0 | Контур source + runtime, импортируемый engine или адаптер, независимые доказательства |
| PentestGPT | Документирует supervisor/executor, deterministic scope/evidence/state; MIT | Организация исследования, memory и trace; зависимости от provider adapters |
| eve | Документирует sandbox bash, файловые инструменты и переопределение tools; Apache-2.0 | Новый TS harness, отключение лишних defaults и локальная интеграция |

Это shortlist, не аудит кода этих проектов и не доказательство их качества.
Лицензии верхнего уровня проверены; перед заимствованием проверяем закрепленный
commit, конкретные файлы, зависимости, NOTICE и возможные отдельные лицензии.
Их benchmark results не переносим в наш отчет и не выдаем чужой результат за наш.

Предварительный порядок: сначала изучить Strix как профильный готовый engine
и OpenHands как coding harness. Сравнить один адаптируемый вариант с небольшим
расширением текущего цикла; не строить сразу четыре полные реализации.
eve остается альтернативой, если реально упрощает контроль tools и deployment.
PentestGPT полезен для сравнения принципов, не обязательная зависимость.

Решение допускает три исхода:

1. Переиспользовать отдельные компоненты и оставить LangGraph.
2. Заменить исследовательский цикл готовым harness, сохранив внешний API и evidence слой.
3. Обернуть готовый pentest engine как отдельный экспериментальный backend.
   Его выводы проходят наш независимый review; непрозрачный engine нельзя
   объявлять соблюдающим наш per-action Validator без соответствующей интеграции.

Сравнение вариантов на DEV: одна модель, одинаковые source/runtime inputs,
одинаковый scope и общий бюджет. При недоступности модели у одного кандидата
сравнение маркируется несопоставимым, а не приписывается качеству harness.
Измеряем реальные tool calls, полезные наблюдения, verified cases, долю ошибок,
число действий, токены, wall time, способность продолжать после неудачи.
Выбираем по этим данным и стоимости интеграции, не по stars и эффектному README.

## 5. Инструменты исследователя

Пока названия ниже — проектируемые capabilities, не новые полномочия.
Каждая проходит существующую или адаптированную границу Validator → Executor.

### 5.1. Файлы

- `list_source_files`: только доверенный inventory, пагинация, исключения.
- `read_source`: relative path, диапазон строк, SHA256 и лимит размера.
- `search_source`: literal/ограниченный regex, file filters, timeout, ограниченные совпадения.
- `write_workspace_file`: только `/workspace`, атомарная запись, digest, ограниченный размер.
- `read_workspace_file`: читать созданные скрипты и результаты.
- Валидация containment, symlinks, traversal, бинарных/больших файлов.
- Исходники `/target` read-only; workspace отдельный, writable, без host mounts.
- `.git`, `.env`, приватные ключи, benchmark labels и операторские сессии
  не попадают в model-visible mount. Простой prompt-exclusion недостаточен.
- Целевые инструкции/комментарии — недоверенные данные, а не команды агенту.

### 5.2. Написание и запуск скриптов

- Python и Node в immutable операторском image; версии и библиотеки закреплены.
- Скрипт создается файлом, не длинным inline argv. Исполнение связывается с
  digest файла, source snapshot, action id и session id.
- Рабочая папка живет в течение исследования, но не между независимыми прогонами.
- Сохраняем command/argv, cwd, digest, stdout/stderr, exit code, duration,
  timeout, output truncation и ссылки на результаты.
- Не устанавливаем packages из интернета в середине измерения. Зависимости
  заранее provisioned оператором и включены в measurement manifest.
- CPU/RAM/PIDs/disk/time limits; отмена убивает дочерние процессы, не только docker exec клиент.
- Никаких ключей LLM, Docker socket, host network, home mounts или production credentials.
- stdout — результат скрипта, а не доверенное описание того, что произошло на сервере.

### 5.3. HTTP и сессии

- `target_http` принимает service id, relative path, метод, параметры и fixture role handle.
- Operator scope может разрешать все пути одного изолированного приложения,
  вместо ручного tool на каждый endpoint. Это явное новое scope-решение,
  зафиксированное в новом профиле, не автоматическое расширение старых профилей.
- Фиксированный broker разрешает service/address из RuntimeServiceMap и
  проверяет каждое обращение: redirects, DNS, private ranges и scope.
- Research container общих команд остается без сети. Если скрипт должен
  формировать серии HTTP-обращений, нужен отдельный broker transport: либо
  пакет предложений HTTP через registered tool, либо защищенный Unix-socket
  proxy в песочнице. Выбрать один вариант после spike; каждый запрос валидируется
  и учитывается в бюджете. Не давать модели host socket.
- Нет произвольного подключения, CONNECT, внешнего DNS/интернета или host gateway.
- Ролевые tokens остаются у broker; модель получает opaque handle, не пароль/token.
- Ограниченные записи допускаются только по operator fixture contract и в disposable target.
- Пробы, control requests, identity checks и cleanup учитываются полностью.
- Ошибка/потеря сессии означает inconclusive, не rejected.

### 5.4. Browser — отдельный следующий инструмент

- Для client-side/DOM поведения нужен браузер, не только HTTP и grep.
- Browser worker имеет собственную restricted network, блокирует внешние
  navigation/subresources/WebSocket/downloads и раскрытие cookies/storage.
- Первый объем: локальная навигация, действия UI, DOM/console/network observations.
- Credentials и управляемое состояние браузера скрыты от модели.
- Browser включаем после HTTP/evidence milestone, не одновременно со всеми инструментами.

## 6. Новый исследовательский цикл

Нужны два уровня: обзор приложения и разбор выбранной гипотезы. Можно реализовать
одним агентом с явным переключением задач; несколько LLM-агентов не обязательны.

1. Собрать surface map: маршруты, роли, middleware, источники ввода, sinks,
   frontend actions, критические объекты. Никаких benchmark answers.
2. Импортировать SAST/DAST observations с provenance; свернуть дубли причины,
   отделить config/dependency/application сигналы. Ничего не удалять из raw artifacts.
3. Завести очередь вопросов: scanner-origin и model-origin равноправны.
4. Выбрать вопрос по ожидаемой полезности, непокрытой поверхности и бюджету,
   а не только по scanner severity/готовому capability.
5. Прочитать связанные файлы. Зафиксировать факты, неизвестное и проверяемое утверждение.
6. Предложить одно действие: read/search/script/HTTP/registered check.
7. Провести approval и execution, сохранить observation и обновить state.
8. Уточнить гипотезу или сменить эксперимент. Семантически одинаковые действия
   без новых данных не повторять; допустимый независимый control/replay отмечать явно.
9. Если доказательство заявлено, передать независимой проверке. Иначе продолжить
   либо закончить с конкретной причиной: budget/unsupported/model_error/policy_denied.
10. Вернуться к очереди. Новая обнаруженная причина создает отдельную гипотезу,
    не теряется в отчете исходного SAST finding.

Политический отказ не обходим синонимом команды. Пока действующая политика
требует terminal denial, сохраняем ее. Новое поведение для recoverable operational
ошибок и разрешенных альтернатив вводим только явным контрактом и тестами.

Контекст не раздуваем бесконечно: ledger фактов и ссылок на raw observations,
обзор незавершенных вопросов, сохраненные важные read ranges и checkpoints.
Сжатие не удаляет ошибки и противоречащие результаты. Provider sessions/SDK
handles не храним в сериализуемом AgentState.

## 7. Доказательства: не строить новый фиксированный tool на каждую находку

Создаем общие протоколы подтверждения эффектов, а не каталог известных ответов
Juice Shop. Агент может выбирать входы эксперимента, но не менять критерий успеха
задним числом после получения ответа.

Для claim нужны: конкретное нарушаемое свойство; source/runtime provenance;
предварительно объявленный experiment contract; собственно observation;
работающие controls; scope результата; независимое воспроизведение, где применимо.

Общие классы evidence: нарушение прав на fixture object; изменение результата
от входа при стабильном контроле; контролируемое раскрытие разрешенного marker;
наблюдение внутреннего sink; client-side effect в browser worker.
Высокий уровень runtime effect не автоматически доказывает произвольный CWE:
семантическая связь с claim проверяется отдельно.

Независимость означает: новый evaluator-owned runner, чистый target generation
и фиксация observations вне model-writable workspace. Сам скрипт агента недоверенный,
он не определяет oracle. Не каждый claim можно автоматически подтвердить:
для неохваченной семантики оставляем review_pending/inconclusive и не считаем confirmed.
В первой версии review_pending может быть report diagnostic без изменения
канонических terminal statuses.

Rejected требует воспроизведения достаточного отрицательного теста и работающих
controls. Отсутствие найденного эффекта, timeout и неподдержанная среда не rejected.
Source proof и runtime proof отображаются отдельно; не выдаем одно за другое.

## 8. Бюджеты, модели и режимы

Два операторских режима: quick CI и deep lab. Значения подобрать на DEV.
Стартовые гипотезы для DEV: quick общий 10–15 минут, deep 30–60 минут;
8–16 действий на исследование с адаптивным распределением, жесткий общий cap.
Это бюджеты проектирования, не обещание времени или результата.

Раздельно лимитируем model calls/tokens, read bytes, workspace bytes, processes,
HTTP requests, browser actions, fixture writes и стоимость provisioning/replay.
Ожидание модели учитывается в wall time; fallback не сбрасывает бюджет.
Новые бюджеты публикуются до измерения, исторический B09 не переписывается.

Qwen Flash — начальный доступный вариант, не окончательный победитель.
Сначала сравниваем harness при одной модели; затем модели при одном harness.
Точные server-advertised IDs и работоспособность проверяем перед испытаниями.
Нельзя по одному запуску приписывать весь результат выбранной LLM.

## 9. Очередность работ и критерии готовности

| ID | Работа | Зависимости | Проверяемый результат |
|---|---|---|---|
| R00 | Зафиксировать baseline, scope и acceptance protocol | Нет | B09 архив сохранен; current code и эталон pinned; правила сравнения записаны |
| R01 | Исследовать готовые engines/harness и выбрать short list | R00 | Матрица лицензий/совместимости/границ; pinned commits; не маркетинговые оценки |
| R02 | Файловый workspace и выполнение скриптов | R00 | Read/search/write/run, сохранение между действиями; isolation/timeout тесты |
| R03 | Scope broker и fixture-aware HTTP | R00 | Каждое обращение валидируется; credentials скрыты; внешняя сеть недоступна |
| R04 | Новый исследовательский цикл за сменным adapter | R01, R02 | Нет early stop только из-за отсутствия готового tool; ledger и budgets |
| R05 | Интеграция обзора, SAST/DAST и queue dedup | R04 | Общая очередь, независимые новые гипотезы, coverage gaps и scanner provenance |
| R06 | Общие evidence protocols и независимый replay | R02, R03 | Script stdout не удостоверяет claim; controls и отдельный reviewer-owned runner |
| R07 | Сквозной DEV acceptance и выбор harness | R03–R06 | Агент сам читает, пишет, запускает, корректирует эксперимент и дает проверяемый результат |
| R08 | Controlled browser для client-side случаев | R03, R06 | Наблюдаемое локальное browser behavior; сеть/сессии/артефакты контролируются |
| R09 | Настройка DEV и модели по карте потерь | R07; R08 для browser cases | Прирост по семействам без удаления сложных случаев из эталона |
| R10 | Freeze + итоговый замер + публикация | R09 | Raw artifacts, confirmed review, metrics/coverage/cost/time, переносимый replay |

R01/R02/R03 можно делать параллельно. Evidence контракт R06 проектируется раньше,
его рабочая приемка требует готовых R02/R03. UI observability разрабатывать
параллельно R04–R07 после фиксации event schema. Browser не блокирует первый
source+script+HTTP milestone, но нужен для заявленного client-side покрытия.

Каждая задача сдает работающий сценарий и доказательства, не только тестовый count.
Первый полезный инкремент: R00/R02/R04, чтение → скрипт → результат → новый шаг.
Второй: R03/R06/R07, реальный эксперимент и независимый verdict.
Третий: широкий поиск/Browser/измерение, R05/R08/R09/R10.

### Обязательные тесты

- Доступ без совпадающего approval/digest/session запрещен; file mutation после
  approval не исполняет незаявленный скрипт.
- Path traversal, symlink, oversized output/file и опасный mount запрещены.
- Прямой egress script/browser, redirects за scope и DNS rebinding заблокированы.
- Ролевые сессии потеряны/перепутаны: no confirmed/rejected.
- Script печатает фальшивый «confirmed»: no confirmed.
- Ложный control, сервер не поднят, stale source, неверная identity: inconclusive.
- Failure одного эксперимента не рушит остальные; сохранен полный след.
- Reset, cancellation, timeout очищают процессы, containers/networks/volumes,
  не затрагивая другие проекты Docker.
- Read/script-only кейс без runtime route продолжается, а не пропадает.
- Отдельные положительные и безопасные fixtures; repository prompt injection
  не меняет scope или target; payload never reaches host execution.
- Полная регрессия старых capabilities, serialization/API/Gate и offline scorer.

## 10. Что означает успешный результат

Техническая приемка: агент самостоятельно проходит multi-step investigation,
не нуждается в человеке для каждого чтения/скрипта, сохраняет факты и корректно
продолжает после неудачи. Нет обходов policy, утечек credentials и host execution.

Качественная приемка: улучшение измеряется не числом alerts, а independent cases.
Отдельно detection recall, confirmed precision/recall, ошибочные rejected,
доля abstention, coverage отрицательных controls, per-family losses и стоимость.
Первая контрольная цель — добиться подтверждений уже найденных случаев и
видимого прироста относительно 13 найденных/5 подтвержденных, без обещания
необоснованного процента. Если прироста нет, выявляем источник потерь до новых функций.

Эталонные 27 случаев сохраняем в знаменателе; unsupported не исключаем тихо.
Дубликаты не увеличивают TP. Внеэталонные claims проверяем отдельно, не записываем
в FP автоматически. Нельзя измерять общую precision, не разобрав остальные confirmed.
Для безопасных случаев требуем реальные эксперименты, а не «не найдено» = TN.

На старом HOLDOUT не настраиваем следующий release; после использования его для
решений он не является полностью независимым. Отдельно фиксируем новые закрытые
cases/проект для проверки переноса, без подглядывания модели в ответы.
Исходное решение пользователя — один итоговый прогон. Пока оно не изменено,
R10 делает один run и отмечает reproducibility=N/A; дополнительные DEV experiments
не объявляются итоговыми повторами. Любое изменение числа итоговых прогонов согласовать.

Scoring accuracy — самостоятельная задача: CP без независимых labels остается N/A;
severity/CVSS требуют совместимой рубрики и обоснованных inputs.
MTTR не появляется от нового поиска: только позже в отдельном fix-контуре
confirmed → patch → independent security/regression verification. Не смешивать
время исследования с временем исправления.

## 11. Видимость пользователю и handoff

В UI показывать текущую гипотезу, выбранное действие, реальную команду, файлы и
диапазоны, созданные скрипты, HTTP role/method/path без secrets, результат,
контрольные наблюдения и причину следующего шага. Не показывать скрытые reasoning
тексты модели; достаточно явного плана, оснований и технических событий.

Handoff содержит pinned commit/model/config/source digests, images, scope,
raw scanner observations, read log, script bytes/digests, commands, HTTP/browser
ledger, approvals, execution/audit, claim dispositions, controls, cleanup и
offline scoring. Secrets, target checkout и окружение не входят в публикацию.
Продолжение после сбоя не перезаписывает предыдущую попытку.

## 12. Что пока не делаем

- Не переносим все на новый стек до comparative spike.
- Не строим автоматическую атаку на произвольные внешние адреса.
- Не включаем tools, обходящие Validator, под видом стороннего harness.
- Не внедряем обязательную армию субагентов, RAG или vector DB.
- Не меняем исторические labels/rules, чтобы получить красивый процент.
- Не объединяем поиск и автоматические исправления в один недоказуемый замер.
- Не закрываем R-задачи по факту написания документа или прохождения synthetic tests.
