# Инженерный паспорт случаев Juice Shop v20.2.0

Статус: J01 завершён; документ относится к разработке и оценке, не к контексту модели.
Эталон: `benchmarks/juice-shop-v20.2.0-v2/ground_truth.yaml`, commit
`5658473cf8814459bf89000ce373b20ed0b4eb37`.

## Граница набора

В рабочем срезе `sample_kind: original` ровно 35 случаев: 27 vulnerable и 8 safe.
Именно они составляют знаменатель исходных метрик. Остальные записи полного YAML
(дополнительные synthetic/patched controls и связанные примеры) используются для
проверки протоколов, но не добавляются к этим 35. DEV: 20 положительных и 2
безопасных; исторический HOLDOUT: 7 положительных и 6 безопасных. HOLDOUT уже
виделся командой и является частью целевого development-набора, а не независимой
оценкой обобщения.

Ожидаемые labels, case ID и привязки из эталона остаются здесь, в evaluator/development
документации. Их нельзя импортировать в `agent`, передавать в prompt, research
context, source projection, tool output или runtime routing. В рабочий контур
передаются только обычные исходники, результаты сканеров, операторские маршруты и
разрешения. Наличие эталонного пути или строки не является finding или Evidence.

## Уровни доказательства и общие правила

| Уровень | Что разрешает утверждать | Что не считается достаточным |
|---|---|---|
| Runtime | Именно описанный эффект воспроизведён в закреплённой лаборатории; есть доступность, личность/роль, baseline, negative control, readback эффекта, запись Executor/audit и успешный reset | Один HTTP 200, вывод модели, наличие строки в коде, невалидный контроль или потерянная сессия |
| Source-condition | Точное свойство исходника независимо разобрано; прослежена связь source → caller → защищаемая операция; есть парсер/контроль для безопасного counterpart | Поиск токена/regex без data-flow, неподтверждённый вызов, предположение о runtime |
| Hypothesis | Сигнал заслуживает проверки; сохраняются provenance и неопределённость | Не засчитывается как runtime confirmation и не превращается в rejected при отсутствии эффекта |

Для каждого активного протокола: начать с readiness/identity и законного базового
запроса; выполнить только фиксированный операторский сценарий; проверить результат
независимым readback; проверить исправленный/безопасный counterpart; закрыть
поколение и проверить cleanup. Отсутствие precondition, поломанный контроль,
недоступный endpoint, timeout, неизвестное состояние или неполный audit означают
`inconclusive/unavailable`, не безопасный результат.

Общие временные и сетевые бюджеты задаются в профиле протокола до запуска. Стартовые
пределы для проектирования: пассивное чтение — не более 4 запросов; фиксированная
проверка одного свойства — до 12; stateful-пара с отдельной подготовкой — до 32;
rate-limit — максимум 12 однотипных запросов плюс baseline. Это верхние границы,
не цель генерировать запросы; протокол обязан остановиться раньше при достаточном
доказательстве. Точный `max_http_requests`, timeout и cleanup-контракт фиксируются
в J09 acceptance до измерительного прогона.

## Статусы и категории потерь для следующего runner

Для каждого case сохраняется текущая стадия первого непройденного перехода:

`detection → normalization/dedup → route binding → fixture preparation →
verification → Evidence/audit → budget/availability`.

Отдельно записываются: `ready`, `failed`, `unsupported`, `not_started`. `unsupported`
не считается safe; он остаётся в положительном знаменателе исходного 27-case
Recall с указанием причины. Для JS-CODE-001 текущая ветка выключена pinned runtime,
поэтому runtime-статус исходного профиля может быть unsupported. JS-CRYPTO-001 и
JS-SAFE-SQL-001 могут получить только отдельный source-condition результат. Ни один
source-only verdict не смешивается с runtime Recall.

J09 должен превратить provisional request ceilings выше в versioned protocol limits,
прогнать positive/safe/broken-control проверки и сохранить время каждого шага,
reset evidence и точную категорию потери. До этой приемки значения являются
инженерными верхними границами, а не измеренным временем.

## Примечания к качеству эталона

Эта матрица конкретизирует инженерные проверки по frozen A04, но не превращает
автоматический source review в независимую человеческую экспертизу. Исходный
`review.yaml` указывает `human_independent_review: not_performed`; это ограничение
происхождения эталона сохраняется в итоговом отчёте.
