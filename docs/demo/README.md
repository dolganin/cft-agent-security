# Демонстрация CFT Security Agent

## Реальный Stage 1 Fix Verification

После подготовки Juice Shop v20.2.0 и локальных images:

```bash
python -m app.stage1_e2e
```

Команда проверяет Docker, immutable image digests, exact target commit и clean
checkout. Если сохранённого report/review нет, получает confirmed report через
реальный Validator/Executor/Evidence и подаёт зарегистрированное SQL-предложение
в обычный strict PatchReview. Затем запускает FixVerificationService.

Каждый запуск сохраняет `artifacts/stage1-e2e/stage1-<unique-id>/`:
`confirmed-report.json`, `patch-review.json`, `fix-verification.json`,
`images.json`, `target-profile.json`, `original-before.json`,
`original-after.json`, persistent execution Evidence и audit.
BEFORE/AFTER работают в новых Docker контейнерах, source checkout не меняется.

Подготовка dependencies выполняется отдельно, исключительно внутри Docker:

```bash
git -c core.autocrlf=false clone --depth 1 --branch v20.2.0 https://github.com/juice-shop/juice-shop.git artifacts/stage1-juice-shop
docker pull python:3.12-alpine
docker build -f docs/demo/fix-verification.Dockerfile -t cft-fix-juice:stage1 artifacts/stage1-juice-shop
```

Checkout должен иметь LF endings: Linux-тесты Juice Shop сравнивают подписи,
зависящие от точных bytes `encryptionkeys/jwt.pub`. Windows CRLF checkout может
падать на двух исходных JWT-тестах до patch. Original checkout не переписывается:
готовится отдельный LF clone того же commit.

Entrypoint разрешает локальные tags только для начального `image inspect` и
сразу фиксирует RepoDigest; runtime использует digest и `--pull never`.
Можно явно передать `--worker-image name@sha256:...` и
`--fix-image name@sha256:...`. Внешняя сеть/install во время verification не нужны.
У upstream v20.2.0 нет lockfile; dependency tree заморожен в provisioned image.
Этот image следует сохранить/распространять по digest для повторения результата.

Опциональные `--report` и `--review` позволяют использовать ранее сохранённые
штатные artifacts. `--target` и `--output-dir` — параметры оператора, не модели.
Output должен находиться вне original checkout.

Два полных реальных прогона с проверкой уникальных sessions и cleanup:

```bash
CFT_RUN_STAGE1_E2E=1 python -m pytest tests/test_stage1_e2e.py -m integration -q
```

В PowerShell задайте `$env:CFT_RUN_STAGE1_E2E = '1'` перед той же pytest командой.
Без opt-in этот дорогой внешний integration test явно skipped.

Подробности реализации и фактические результаты:
[`stage1-fix-verification-report.md`](../stage1-fix-verification-report.md).

Для demo API/UI добавьте в операторский registered TargetProfile после
provisioning (подставьте фактический `docker image inspect ... RepoDigests`):

```yaml
fix_verification:
  adapter: juice_node_v1
  image: cft-fix-juice@sha256:<actual-64-hex-digest>
  service: juice
  source_commit: 5658473cf8814459bf89000ce373b20ed0b4eb37
  timeout_seconds: 300
  wall_clock_budget_seconds: 1800
```

Нужен LF target checkout. Без этого операторского config API возвращает
INCONCLUSIVE с `security_verified=false`; модель не подбирает image/команды.
Proposal artifact остаётся read-only историей ревью; результат выполненной
проверки показывается и сохраняется отдельным Fix Verification artifact.

Это короткий проход для презентации 9 октября, не замена полного бенчмарка.

[Проверенный результат реального прогона 8 октября](verified-result-2026-10-08.md).

## Что говорить о продукте

> Мы разрабатываем агента для анализа безопасности в CI/CD. Он объединяет
> статический анализ и исследование исходников моделью, учитывает контекст
> приложения, а затем проверяет гипотезы в изолированном окружении. Разработчик
> видит не только предупреждение сканера, но и выполненную проверку,
> доказательства, ограничения вывода и решение для CI.

Ценность, которую хотим подтвердить на следующих измерениях: меньше ручной
работы по разбору находок, понятный приоритет и проверенные исправления.
Экономия времени и полнота обнаружения пока не доказаны этим демо.

## Сценарий показа на 3-5 минут

1. Открыть `http://127.0.0.1:5173/demo`. Объяснить проблему: предупреждение
   сканера само по себе не доказывает эксплуатацию.
2. Показать схему. Модель не выполняет действия напрямую, разрешение дает
   детерминированный валидатор.
3. Открыть завершенный реальный прогон кнопкой «Открыть действия и
   доказательства». Для живого показа нажать «Новый демонстрационный прогон».
   Не обещать фиксированное время: скорость внешней модели меняется.
4. Раскрыть SQL-находку, гипотезу и инструмент проверки. Показать привязку
   к разрешенному endpoint и Docker session.
5. Раскрыть доказательство. SQL-проверка сравнивает ограниченные контрольные
   запросы; проверка каталогов наблюдает список имен и типы файлов, не
   скачивает содержимое секретов.
6. Показать находку с недостаточными данными. Успешный вызов инструмента
   не равен подтвержденной уязвимости.
7. Завершить решением CI. `exit=1` может означать завершенный анализ с
   проблемой безопасности, `exit=2` означает технический сбой.
8. Вернуться на экран демо. Раскрыть «Предложение исправления»: настоящий
   ответ модели для SQL-находки в поиске товаров, diff и скачивание патча.
   Пояснить: область и формат проверены, но сборка и before/after еще не
   выполнялись. Это не автоматическое устранение уязвимости.

## Как работает текущий контур

```text
Код + доверенный профиль
  → Discovery
  → SAST + ограниченный поиск модели по исходникам
  → очередь находок + контекстный приоритет
  → гипотеза и следующий шаг агента
  → Validator
      разрешено → Executor в Docker → Evidence → переоценка
      запрещено → отчет с отказом политики
  → FinalReport → решение для CI/CD
```

Scout может запросить дополнительные окна исходников и буквальный поиск.
Кандидаты привязаны к прочитанным строкам. Карта прямых Express-регистраций
помогает найти связанные обработчики, но не доказывает наличие или отсутствие
авторизации и не расширяет разрешения сети.

## Объем именно этого демо

- Juice Shop 20.2.0, исходный commit
  `5658473cf8814459bf89000ce373b20ed0b4eb37`.
- Docker-образ закреплен по SHA-256; изолированная внутренняя сеть, без
  опубликованных портов, bind mounts и доступа к ключам агента.
- Свежий Semgrep, два выбранных правила: потенциальная SQL-интерполяция
  в `routes/login.ts` / `routes/search.ts` и вызовы `serveIndex` в `server.ts`.
- Дополнительно Scout: максимум 2 обращения к модели и 4 кандидата;
  ограничение времени 60 секунд проверяется между ходами. Это не гарантирует
  жесткую остановку сетевого запроса ровно на 60-й секунде.
- Для демо явно выбран маршрут NSU `Qwen3.8-27B`, уровень рассуждений `low`,
  до 8192 выходных токенов и таймаут отдельного обращения 55 секунд.
  Основная цепочка моделей в `.env` от этого не меняется.
- Для каждой находки максимум 2 действия. Остаток исходников не считается
  просмотренным, кандидаты не считаются подтвержденными без Evidence.
- SQL-наблюдение подтверждает поведение конкретных контрольных запросов;
  это не полный аудит всех SQL-путей. Доступный список чувствительных имен
  не доказывает возможность скачать содержимое этих файлов.
- `WARNING` у Semgrep является уровнем предупреждения сканера, не CVSS.
  Универсальный расчет CVSS и разметка Context Priority по эталону не
  демонстрируются как завершенные метрики.

Профиль и привязки runtime операторские. Нормализация семейства Scout/SAST
позволяет использовать одну возможность проверки, только если точные файл,
строка, endpoint и режим разрешены профилем. Одна карта маршрутов такого
разрешения не дает.

## Запуск на этом компьютере

В корне репозитория, Docker должен быть запущен:

```bash
env -u NSU_OPENWEBUI_KEY PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m app.demo
```

`env -u` убирает устаревший ключ только из окружения этого процесса, чтобы
использовался локальный `.env`. Это не меняет глобальные настройки системы.
Ключи не включаются в документы или результаты запуска.

Во втором терминале:

```bash
cd frontend
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

Сервер демо занимает `127.0.0.1:8080`. Он использует отдельную SQLite базу
`api_data/presentation-2026-10-08.sqlite3` и каталог
`artifacts/presentation-2026-10-08/runs`, не подменяя старые метрики или историю.
Не запускайте основной API на том же порту одновременно.

Проверить, что commit совпал с указанным выше, прежде чем использовать

разрешений на похожие строки.

## Где проверять результат

Каждый запуск сохраняет:

- `demo-scope.json`: явное ограничение объема, версия и параметры;
- `sast/findings.json`: свежие статические находки;
- `scout/summary.json`: реально рассмотренные строки и причина остановки;
- `scout/candidates.json`: гипотезы модели;
- `scout/express-source-map.json`: ограниченная карта регистраций;
- `audit/llm-attempts.jsonl`: реально ответившая модель и случаи fallback;
- `audit/executor.jsonl`, `evidence/`, `reports/`: действия и доказательства;
- `gate.json`, `ci-summary.json`: итог и техническое состояние.

Запрошенная модель и реально ответившая могут различаться. Успех резервного
маршрута не означает, что DeepSeek тоже ответил. Если все модели недоступны,
детерминированный fallback не представляется как живое рассуждение LLM.

## Что пока не обещаем

В демо есть предложение патча для `routes/search.ts:23`. Модель получает
только окно 18-25, меняет операторское окно 20-23; комментарии с разметкой
бенчмарка удаляются из модельного контекста. Детализация проверки:

- исходное условие должно совпадать с завершенным confirmed-отчетом;
- фиксируется SHA-256 текущего файла и предложения;
- проверяются все поддержанные заголовки diff, точный контекст и счетчики;
- другие файлы, metadata/rename/binary, symlinks и расширение окна запрещены;
- выбранный SQL-запрос сохраняет SELECT, фильтр, порядок и LIKE-шаблон;
- согласованность `:name`/`replacements` и `$name`/`bind` проверяется согласно
  [документации Sequelize v6](https://sequelize.org/docs/v6/core-concepts/raw-queries/).

Первая попытка модели смешала эти API и была отклонена при ревью.
После добавления проверки следующая попытка прошла scope/format review.
Предыдущий артефакт сохранен в `patch-reviews/`, новый в `patch-review.json`
и `proposal.patch`; отдельный журнал модели в `audit/patch-llm-attempts.jsonl`.

Это синтаксически проверенное предложение. Не выполнялись применение,
сборка, тесты или повтор security-проверки измененной программы. `applied`
и `security_verified` всегда `false`; первоначальный Gate не меняется.
Старая заготовка `FixVerificationService` с host test execution к этому
пути не подключена.

Автоисправление и автоматический PR в этом демо не включены. Следующая цель:
патч в отдельной копии проекта, тесты, повтор исходной проверки и передача
изменений разработчику на ревью. Production-проверки не входят в MVP.

Этот запуск не измеряет полный recall, воспроизводимость между несколькими
прогонами или MTTR. Для них нужен отдельный заранее зафиксированный протокол.
