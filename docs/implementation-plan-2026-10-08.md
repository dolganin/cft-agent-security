# Подробный план реализации CFT Security Agent

Дата: 8 октября 2026 года.

Статус документа: план разработки, не отчет о выполнении. Код и конфигурация в рамках подготовки этого плана не изменялись. Оценки времени ниже являются оценками инженерной работы, а не обещаниями длительности внешних LLM-запросов.

Ближайший этап подробно раскрыт в [плане надежного Scout, карты Express и проверки находок](development-stage-scout-routing-verification-2026-10-08.md): задачи, shared contracts, тестовая матрица, реальные прогоны и приемка.

## 1. Какой результат строим

Цель ближайшей реализации: агент самостоятельно расширяет поиск за пределы SAST, связывает кандидатов с кодом и доступными маршрутами, выполняет разрешенные проверки, объясняет доказательства и для ограниченного класса подтвержденных проблем предлагает и проверяет исправление в изолированной копии проекта.

Цель демонстрации: показать один настоящий проход с проверяемыми артефактами, а не впечатляющее количество непроверенных сообщений.

Цель недельной доработки: получить измеримый прирост относительно зафиксированного baseline на Juice Shop, несколько сопоставимых запусков и честные метрики с заранее определенными знаменателями.

Рабочая последовательность:

```text
Доверенный профиль + снимок репозитория
  → Discovery + карта маршрутов/обработчиков
  → SAST + поиск кандидатов по исходникам
  → нормализация и объединение Finding
  → CVSS / Context Priority
  → существующий LangGraph
      гипотеза → план → Validator → Executor → Evidence → переоценка
  → FinalReport + Gate
  → при отдельном включении: предложение исправления
      → Validator → изолированная копия → Executor
      → тесты и повтор исходной проверки → артефакт исправления
```

Исправление является дополнительным процессом после подтверждения. Оно не создает обход Validator/Executor и не переписывает первоначальный отчет. Исторический Gate первоначального запуска сохраняется; новый анализ исправленной копии имеет отдельные идентификатор, доказательства и решение.

## 3. Главные технические проблемы

### 3.1. Неполное чтение не равно отсутствию уязвимостей

Scout ограничен числом файлов, размером файлов, символами, ответами модели и временем. Текущие базовые значения: 256 файлов в корпусе, 4 МиБ корпуса, 128 КиБ на файл, 160 строк/10000 символов на окно, 8 шагов, 160000 новых символов, 240 секунд. Память повторного контекста ограничена отдельно.

Поэтому нужно показывать три разные величины: обнаруженные файлы проекта, включенные в корпус файлы и успешно переданные в контекст участки. Даже корректный ответ модели не доказывает внимательное понимание каждой переданной строки. В пользовательском отчете это называется покрытием контекстом, а не гарантированным анализом всего проекта.

### 3.2. Модель видит sink, но не всегда видит защиту

Нельзя объявлять отсутствие авторизации только по обработчику: защита может находиться в `app.use`, цепочке middleware, подключенном Router или вызываемой функции. Нужна карта с порядком регистрации, связями и явными неизвестными.

### 3.3. Новая находка может не получить применимую проверку

Поиск и проверка сейчас развиты неравномерно. Scout может вернуть семейство `sql-injection`, а runtime-подбор ориентируется на конкретное правило Semgrep и `file:line` metadata. При улучшении поиска без улучшения привязки проверок мы получим больше inconclusive, а не больше подтвержденных результатов.

### 3.4. Повторные действия тратят время без нового знания

Нужны учет уже проверенных гипотез, сигнатуры действий и ограничение повторов. Повторный запрос допустим как заранее описанный контроль воспроизводимости, но не как бесконечная попытка получить другой вердикт.

### 3.5. Текущая заготовка исправления недостаточно изолирована

Временный каталог, ограниченные переменные окружения и запрет некоторых имен команд не являются полноценной границей исполнения. Сейчас проверки патча вызываются через `subprocess.Popen` на хосте. Кроме того, статус `verified` зависит от успешных проверок с метками static/runtime, но сами метки и exit code еще не доказывают устранение первоначальной проблемы.

Это приоритетный блокирующий пункт для автоисправления, не косметическая доработка.

### 3.6. Измерение качества нельзя отложить до конца

Количество кандидатов, число SAST-сигналов, количество уникальных дефектов и количество задач Juice Shop являются разными единицами. Эталон, правила сопоставления и отрицательные случаи нужно заморозить до оценочных запусков.

## 4. Правила, которые не меняем

1. Существующий LangGraph и общие схемы сохраняются; перенос на новый агентный фреймворк не нужен.
2. Scout работает только с ограниченным доверенным корпусом; его запросы являются чтением данных, не командами.
3. Каждый активный шаг, включая применение патча и проверку исправления, проходит детерминированный Validator.
4. Исполнение генерируемого/целевого кода допускается только в disposable Docker lab через зарегистрированные возможности Executor.
5. Общие sandbox-команды не получают сеть. Проверки target runtime используют отдельные trusted возможности и только разрешенную внутреннюю сеть.
6. Нет монтирования Docker socket, каталогов пользователя, SSH-конфигурации, реальных API-ключей или среды хоста в target-контейнер.
7. Production, произвольные внешние адреса и извлечение реальных учетных данных исключены.
8. Модель не назначает себе разрешения и не задает окончательный численный CVSS.
9. Подтверждение исходного условия явно отличается от runtime-подтверждения поведения.
10. Неполный анализ, отказ политики и техническая ошибка не выдаются за отсутствие уязвимостей.
11. Исправление в копии не равно принятому исправлению в основном проекте или выполненному деплою.
12. Не раскрываем скрытые рассуждения модели: показываем краткую проверяемую гипотезу, цель действия, факты и решение.

## 5. Этап P0. Зафиксировать рабочую исходную точку

Оценка: 1–3 часа. Исполнитель: Ставр, при проблемах runtime вместе с Кириллом.

### Задачи

1. Разобрать текущий dirty tree на изменения этого этапа, предыдущую работу и посторонние файлы. Не использовать общий `git add .`.
2. Зафиксировать HEAD, список релевантных изменений и статус тестов. Сравнить с актуальным main; интеграцию выполнять отдельно, без стирания чужой работы.
3. Запустить backend suite, Ruff, `python -m app.main`, frontend tests и build. Docker-интеграции выделить отдельно; skips перечислить с причиной.
4. Добавить/проверить регрессии последних изменений Scout: round-robin, память без готового кандидата, совокупный бюджет поиска и чтения, учет только успешных ответов.
5. Выполнить безопасный preflight LLM: проверка доступных моделей, один минимальный структурированный ответ, поддержка используемого reasoning effort, таймаут. Ключи не выводить.
6. Явно показывать источник конфигурации: shell override или локальный конфиг, только названия источников, без значений секретов. Не менять ключ или маршрут молча.
7. Зафиксировать точный commit Juice Shop и профиль запуска. Development/diagnostic артефакты не называть benchmark.

### Проверки

- Полный граф детерминированного сценария не изменил терминальные статусы.
- Отказ LLM не уничтожает SAST-результаты и ранее принятые Scout-кандидаты.
- Cancellation завершает работу, а не превращается в `model_unavailable`.
- Одна техническая ошибка finding не теряет остальные отчеты.
- В диагностике нет ключей, токенов и абсолютных путей пользовательского окружения в API.

### Критерий приемки

Есть проверенная исходная точка, известные проваленные/пропущенные тесты перечислены, рабочий модельный маршрут проверен отдельно от поиска. До завершения P0 не приписываем последним изменениям измеренный прирост качества.

## 6. Этап P1. Довести поиск по исходникам до надежного компонента

Оценка: 3–6 часов. Основной исполнитель: Ставр.

### P1.1. Политика корпуса и защита от подсказок

Работа в существующих RepositorySource и Discovery.

- Выделить версионируемую политику включения/исключения. Для Juice Shop явно исключить codefixes, instructor/solutions, benchmark/oracle и challenge-разметку из модельного контекста.
- Зафиксировать одинаковую область для сопоставимого baseline и агентного поиска. Результаты SAST вне области можно сохранять отдельно, но не включать незаметно в основной benchmark.
- Не исключать реальные runtime-модули только потому, что в имени есть `challenge`: назначение проверяется по структуре проекта. Решения и таблицы эталона не должны попадать в Scout.
- Проверить абсолютные пути, `..`, символические ссылки, ссылки в родительских каталогах, бинарные и слишком большие файлы.
- Маскировать распознаваемые секретные литералы, не уничтожая поток `req.body.password` и нумерацию строк. Маскирование не превращать в доказательство безопасности.
- Записывать digest исходного снимка, версии политики, число eligible/indexed/excluded файлов и причины исключения.
- Для существенных ограничений размера сохранять список пропущенных путей с безопасной причиной, а не только общий счетчик.

### P1.2. Покрытие и бюджеты

- `submitted_ranges`: отправлено в запросе.
- `reviewed_ranges`: запрос завершился корректным структурированным ответом; это не гарантия обнаружения всех дефектов внутри.
- Считать уникальные строки по объединению интервалов, не суммировать повторно перекрывающиеся окна.
- Учитывать поиск, новое чтение и повторный контекст отдельно. Ограничивать также полный размер каждого запроса, число входных/выходных токенов при доступности учета и общее число вызовов.
- Определить, учитываются ли подготовленные, но не отправленные результаты поиска: назвать их отдельно, не включать в успешное покрытие.
- Отдельно контролировать число кандидатов. Настраиваемый предел отражается как `candidate_budget`, когда следующий уникальный кандидат не помещается.
- Добавить однозначные stopping reasons: `completed`, `no_application_source`, `source_budget`, `turn_budget`, `candidate_budget`, `wall_clock_budget`, `model_unavailable`, `cancelled`.
- Для пустого корпуса и раннего сбоя сохранять такой же полный summary, как для успешного запуска.

### P1.3. Очередь исследования

- Сохранить round-robin между файлами; добавить справедливость между обнаруженными компонентами.
- Сначала входные точки и опасные операции, затем зависимости и остальной код.
- Запросы модели приоритетнее обычного обхода, но не могут бесконечно вытеснять другие компоненты.
- Повторное чтение уже переданного диапазона разрешать только при явной причине и с учетом бюджета.
- При необходимости расширить число шагов и кандидатов конфигурационно, после измерения стоимости. Согласовать изменения общего ограничения CandidateFindingBatch со всеми потребителями; не просто поменять одну константу.

### P1.4. Память исследования

Добавить ограниченную сериализуемую память, без SDK-объектов:

- подтвержденные чтением факты с точными source anchors;
- открытые вопросы и неизвестные предусловия;
- уже рассмотренные подозрения и обнаруженные защитные механизмы;
- связи функций/маршрутов;
- ожидаемые дополнительные файлы;
- рассмотренные кандидаты и причины отказа.

Модельное резюме не является фактом без ссылки на прочитанный участок. Приложение проверяет anchor и хранит границу между фактом, предположением и нерешенным вопросом.

### Тесты P1

1. Кандидат за пределами прочитанных строк отвергается.
2. Кандидат через непрочитанный разрыв отвергается.
3. Ссылка на файл, найденный поиском, но еще не прочитанный, не превращается в полное доказательство.
4. Сбой запроса не увеличивает успешное покрытие.
5. Большой файл не блокирует остальные компоненты.
6. Новый контекст не превышает общий бюджет после нескольких поисков.
7. Исследование сохраняет вопрос между stateless запросами даже без кандидатов.
8. Попытка prompt injection в комментарии не меняет tool/policy scope.
9. Каталоги с ответами отсутствуют во всех сохраненных payload, включая related/search/memory.
10. Достижение candidate cap явно отражается в summary.

### Критерий приемки

Чистый source-only запуск на закрепленном Juice Shop, с сохраненными артефактами, без подсказок из эталона и без ложного заявления о полном покрытии. Все принятые кандидаты вручную просмотрены: результат ревью отделен от автоматического вердикта. Не требуем произвольного количества находок как условия успеха.

## 7. Этап P2. Построить карту маршрутов, функций и защитных проверок

Оценка: 4–8 часов для ограниченной поддержки Express/TypeScript. Основной исполнитель: Ставр; trusted runtime binding совместно с Ромой и Кириллом.

Это следующий ключевой этап после проверки нынешнего Scout. Первая поддерживаемая платформа соответствует Juice Shop. Django и другие стеки добавляются позднее через отдельные адаптеры, не в рамках универсального анализатора за один день.

### P2.1. Контракт карты

Сначала проверить возможность расширения существующих discovery/runtime схем. Если нужны новые общие сущности, добавить их в `schemas/`, не создавать локальные дубликаты Finding или Evidence.

Для каждой source-привязки нужны:

- service/component ID;
- HTTP method и нормализованный путь либо `unknown`;
- source-файл и диапазон регистрации;
- обработчик и диапазон его определения;
- порядок middleware и mount prefixes;
- распознанные проверки authentication/authorization/ownership;
- входные поля и связанные операции в пределах поддерживаемого анализа;
- происхождение связи и версия адаптера;
- unresolved части и причина неполноты.

Наличие middleware с названием `authenticate` не доказывает корректность проверки. Карта утверждает наличие и порядок вызова; семантика защитного решения проверяется отдельно.

### P2.2. Ограниченный source parser

- Выбрать и зафиксировать парсер через небольшой технический эксперимент: реальные файлы Juice Shop, точные строки, TS/JS синтаксис, отсутствие исполнения проекта, лимиты времени/памяти.
- Предпочитать AST для поддерживаемых конструкций. Regex допустим как candidate hint, но не как доказательство отсутствия защиты.
- Поддержать `app.get/post/put/delete`, `router.*`, цепочки middleware, подключения Router, импортированные обработчики и `app.use` с учетом порядка.
- Рассчитать mount prefix и endpoint только для однозначных статических выражений.
- Для динамических путей, вычисляемых wrappers, неизвестных импортов и неподдерживаемых конструкций вернуть `unknown`, а не удобную догадку.
- Не выполнять JS/TS, package scripts, импорты проекта или его конфигурацию для построения карты.
- Не строить глобальный межпроцедурный taint-analysis MVP. Начать с route → handler → ближайшие helper functions.

### P2.3. Подключение к Scout

- Передавать небольшую релевантную часть карты вместе с окнами кода.
- Дать модели возможность запросить маршрут/обработчик по ID, а не произвольный путь хоста.
- Для кандидата сохранять связь с route ID и указание защиты: присутствует, отсутствует в поддерживаемом scope, неизвестна.
- Если не прочитана цепочка middleware, кандидат содержит неизвестное предусловие и не описывается как доказанное отсутствие авторизации.
- Проверить глобальные guards до локальных выводов.

### P2.4. Trusted runtime binding

Карта исходников является предложением привязки, не разрешением на сеть.

1. Приложение связывает route с обнаруженным компонентом.
2. Runtime подтверждает зарегистрированный service в конкретной sandbox session.
3. Операторская политика разрешает только нужное подмножество source-derived маршрутов.
4. Validator проверяет method, параметры, role/test identity, квоты и допустимую операцию.
5. Executor обращается к точному internal service; запрет внешних redirect-follow остается обязательным.

Metadata по точному `file:line` сохраняется как совместимый override, но для поддерживаемых классов не является обязательным единственным способом привязки. Сдвиг строк не должен автоматически отключать проверку.

### Тесты P2

- Guard до маршрута и guard после него дают разный результат.
- Router mount prefix правильно объединяется с локальным путем.
- Общий middleware, inline guard и импортированный handler сохраняют порядок.
- Публичный endpoint не считается уязвимостью только из-за публичности.
- Неоднозначный маршрут не получает автоматически trusted network binding.
- Несуществующий URL, внешняя ссылка и пересечение границ service отвергаются.
- Сдвиг строки не ломает привязку к тому же handler.

### Критерий приемки

Для выбранных реальных SQL, файловых и read-only access-control кандидатов отображается цепочка route → middleware → handler → relevant operation. Неизвестные части явно обозначены. Модель не задает hostname, base URL или дополнительные права доступа.

## 8. Этап P3. Нормализация, происхождение и дедупликация

Оценка: 2–4 часа. Исполнитель: Ставр.

### Задачи

- Ввести единый normalizer семейств для SAST, Scout и выбора verifier. Это устраняет разрыв между `sequelize-injection` и `sql-injection`.
- Проверить коллизии SAST ID. Исходный scanner ID сохранить, внутреннюю уникальность гарантировать на уровне конкретной операции и source snapshot.
- Для совпавших SAST/Scout находок сохранять обе ссылки происхождения и Scout rationale. Сейчас совпадение может просто отбросить дополнение Scout.
- Различать occurrence ID для конкретного запуска и semantic fingerprint для сопоставления между запусками/патчами.
- Fingerprint строить из нормализованного семейства, пути, handler/sink и доступной нормализованной структуры кода. Строки являются anchor, но не единственным ключом межверсийного сравнения.
- Не объединять две независимые операции на одной строке и разные семейства.
- Не склеивать широкие пересечения диапазонов без достаточных признаков одного дефекта. Неоднозначность сохранять как связь possible_duplicate.
- Сохранить объяснимый merge log: что объединено, почему, какие original IDs относятся к результату.
- Выполнить scoring для итоговой канонической очереди; никакая находка Scout не должна обходить Context Priority.

### Критерий приемки

Два одинаковых входа дают одинаковую очередь и fingerprints; перестановка входных записей не меняет результат. Числа raw signals, unique candidates, unique findings и matched benchmark cases публикуются отдельно.

## 9. Этап P4. Расширить проверки на несколько полезных семейств

Оценка: 8–16 часов на три ограниченных класса. Исполнители: Рома + Кирилл, интеграция Ставра.

Порядок: SQL и файловые поверхности, затем read-only access control. Browser/XSS включается в недельный backlog и не блокирует базовое демо.

### P4.1. Общий механизм выбора проверки

- Из существующего `verification_candidates` выделить подбор по нормализованному семейству, source facts, route binding и реальным возможностям runtime.
- Модель выбирает из разрешенных стратегий и объясняет цель. Приложение заполняет target, service, endpoint, artifact IDs и iteration/action IDs.
- Новый verifier является переиспользуемым классом, не функцией для единственной строки Juice Shop.
- Для каждой стратегии описать нужные предусловия и допустимые terminal observations.
- Если стратегия неприменима, показать точную причину: route unresolved, runtime unavailable, fixture missing, unsupported family, policy blocked, budget exhausted.
- Расширять существующие `schemas/security_tools.py`, registry, Validator и Evidence interpreter согласованно. Не создавать второй свободный executor.

### P4.2. SQL

- Сначала определить источник ввода, построение запроса и наличие параметризации/нормализации.
- Переиспользовать имеющуюся bounded SQL проверку, обобщив binding на Scout-кандидаты и разные поддерживаемые handlers.
- Runtime-проверка использует ограниченные недеструктивные дифференциальные наблюдения и контрольные запросы.
- Для подтверждения нужны повторяемость наблюдения, валидный baseline и отсутствие более простого объяснения ошибки.
- Не извлекать таблицы, пароли и токены; не считать любой HTTP 500 доказательством SQL-инъекции.
- Для authentication-класса предусловия должны быть отдельно разрешены, без сбора реальных учетных данных.

### P4.3. Файловый доступ и публикация каталогов

- Определить намеренно публичный asset и потенциально чувствительную поверхность по независимой спецификации, а не по имени файла.
- Начать с метаданных/списков и синтетических файлов, не скачивать чувствительное содержимое.
- Для traversal использовать только ограниченный lab-owned marker внутри изолированной копии/контейнера и заранее разрешенную процедуру.
- Контрольный безопасный путь должен продолжать работать.
- Открытый каталог без доказательства чувствительности не автоматически confirmed vulnerability.

### P4.4. Access control

- Создать две синтетические test identity и принадлежащие им тестовые объекты только внутри disposable lab.
- Для первого MVP разрешить read-only проверку ownership; операции изменения объектов добавлять отдельной политикой позже.
- Зафиксировать owner/role ожидания в операторском тестовом профиле.
- Подтверждать нарушение только по структурированному сравнению разрешенного и запрещенного наблюдений, а не по одинаковому статусу 200.
- Не использовать production cookies и реальные пользовательские данные.
- После каждой проверки сбрасывать fixture или уничтожать session; все мутации setup имеют ограниченный зарегистрированный путь и отдельное разрешение.

### P4.5. XSS, после базового демо

- Пока сохранять source-flow check с явно статическим scope.
- Для runtime-подтверждения потребуется отдельная изолированная браузерная возможность, безопасный marker, контроль sanitizer и запрет внешних запросов.
- Не выдавать наличие `dangerouslySetInnerHTML` само по себе за доказательство исполнения.

### Evidence и rejected

- Typed worker output должен быть связан с одобренным action, artifact, route и session.
- Вывод generic sandbox command, даже похожий на JSON verifier, остается наблюдением, а не доверенным вердиктом.
- `confirmed` требует достаточного доказательства заявленного условия в указанном scope.
- `rejected` требует достаточного опровержения именно этой гипотезы. Неудачная попытка эксплуатации сама по себе недостаточна.
- `inconclusive` содержит конкретный следующий недостающий факт.
- Добавить поддерживаемый `rejected` в новые bounded схемы только вместе с четкими правилами интерпретации и регрессиями.

### Критерий приемки

В каждом реализованном классе есть уязвимый и защищенный локальный тестовый случай. Их исход известен заранее. Нельзя получить confirmed, подделав stdout или модельный ответ. Хотя бы один новый source-backed кандидат вне очереди SAST проходит каноническую проверку; если на целевом снимке такого случая не найдено, это честно фиксируется, а компонент проверяется на отдельном fixture.

## 10. Этап P5. Надежность LLM, графа и запусков

Оценка: 3–6 часов; часть делается вместе с P1/P4. Исполнители: Ставр + Кирилл.

### Бюджеты

- Передавать общий абсолютный deadline во все модельные маршруты и активные действия.
- Таймаут отдельного запроса не превышает оставшееся время; failover не начинает новый полный бюджет.
- Ограничить суммарные вызовы на исследование, finding и run.
- На повторяемый schema error допускается один контролируемый repair; не бесконечный цикл.
- На временные 429/5xx/network допускается ограниченный retry с backoff в пределах deadline. На 401/403 и отсутствующую модель не повторять тот же неработающий запрос бесконечно.
- Неподдерживаемый reasoning effort не подменять случайно: адаптация привязана к конфигурации provider и покрыта тестом.

### Память и действия

- Учитывать сигнатуру tool + normalized params + service + endpoint + hypothesis.
- Допускать повтор только как необходимый контроль, с причиной и лимитом.
- При отсутствии новой информации завершать finding с конкретным stop_reason.
- Один сбой capability не останавливает весь run; технический статус при этом не прячется под успешный security verdict.
- Сохранять checkpoint после каждого завершенного finding и этапа Scout.
- Повторный запуск создает новый run ID; использование cache/resume маркируется и не считается независимым повтором benchmark.

### Runtime lifecycle

- Readiness проверяется до активных действий, healthcheck timeout объясним.
- У run собственные resource quotas и session identifiers.
- Cancellation/timeout освобождает контейнеры, сети и временные данные конкретного run.
- Cleanup не затрагивает чужие контейнеры, wiki и другие локальные проекты.
- Общие quotas для параллельных запусков не обходятся новыми verifier/fix контейнерами.

### Критерий приемки

Регрессии на model timeout, schema error, unavailable model, container not ready, action timeout и cancellation сохраняют частичные артефакты, корректно завершают run и не оставляют его зависшим или ложноположительно успешным.

## 11. Этап P6. Безопасное предложение и проверка исправления

Оценка: 8–16 часов для одного класса. Исполнители: Ставр + Рома + Кирилл.

Не начинаем с «исправь весь проект». Первое исправление выбирается по зрелости проверки и минимальности изменения. Предпочтение: небольшой дефект с ясным существующим тестом и надежной before/after проверкой, например безопасная параметризация запроса, если конкретный слой это позволяет. Не обещаем заранее, что исправление обязательно будет успешным.

### P6.1. Вход и контракт

Переиспользовать ProposedPatch/FixVerificationArtifact, при необходимости расширить их совместимо:

- confirmed report ID и digest исходного снимка;
- точный scope доказательства, не только строка status;
- допустимые файлы, предел размера diff, причина изменения;
- отдельный fix ID и связь с исходной гипотезой;
- запрещенные классы изменений;
- план повторной проверки из trusted profile;
- временные метки proposal, application, tests, verified/rejected;
- ссылки на persisted artifacts и sandbox session.

Не сохранять sdk handles. Старые JSON читаются через совместимые defaults или явную версию/миграцию.

### P6.2. Генерация предложения

- LLM получает подтвержденное условие, релевантные окна, маршрут, ограничения и факты.
- Возвращает только минимальный unified diff и краткое объяснение.
- Не выбирает команды, не ослабляет policy/verifier, не меняет эталон и не удаляет проверки.
- По умолчанию один файл. Дополнительный файл допускается только заранее разрешенным расширением scope, а не по инициативе модели.
- Для candidate/inconclusive допустима рекомендация, но не автоматическое применение как подтвержденного исправления.

### P6.3. Детерминированный Patch Validator

- Проверить finding ID, snapshot digest, целевой scope и размер diff.
- Разбирать все старые/новые paths, rename/delete/add и специальные заголовки, а не только строки `+++`.
- Запретить абсолютные пути, `..`, symlink escapes, binary patches и изменения режима/специальных файлов вне явно разрешенного случая.
- Запретить изменения тестового oracle, capability worker, политик, benchmark labels, lockfile/зависимостей и CI, если они не входят в отдельный согласованный scope.
- Запретить ослабление теста или удаление защитной функциональности как способ «починки».
- Проверить применимость diff к исходному снимку; при несовпадении остановиться, не force-apply.
- Одобрение связать с digest полного предложения; после мутации diff исполнение запрещено.

### P6.4. Изолированное применение и тесты

- Убрать host execution из product-пути FixVerificationService. Сохранить тестируемую оболочку и данные, но направить действия через Validator/Executor.
- Создать disposable patched workspace из точного target snapshot. Исходный проект остается read-only.
- При копировании не следовать ссылкам за root; исключить реальные .env, credentials, окружение, кэши и лишние артефакты.
- Записать diff и применять его фиксированной capability в копии.
- Compile/unit/static проверки исполняются в networkless Docker; stdout/stderr ограничиваются и маскируются.
- Зависимости готовятся операторским reproducible build-процессом, не произвольным model-selected install с интернетом во время проверки.
- После патча отдельный trusted runtime поднимается из измененного снимка. Возможности runtime наблюдения обращаются только к его внутренней сети.
- Не давать model sandbox Docker socket или возможность управлять чужими контейнерами.

### P6.5. Before/after и смысл verified

Успешный exit code или название `kind=runtime` не являются достаточным подтверждением исправления.

Для `verified` необходимо одновременно:

1. исходная проверка воспроизводит исходное подтвержденное условие;
2. patch применен к правильному snapshot;
3. измененная версия собирается, если сборка требуется;
4. необходимые регрессионные/функциональные тесты проходят;
5. исходная security-проверка на новой версии больше не подтверждает дефект и дает достаточный ожидаемый безопасный результат;
6. контрольный разрешенный сценарий продолжает работать;
7. verifier и тестовый эталон не изменены патчем;
8. все результаты связаны с новым snapshot/session и сохранены.

Timeout, недоступный runtime и недостаточные наблюдения дают `inconclusive`, а не verified. Сохранившаяся проблема или сломанная функциональность дают `not_verified`.

### P6.6. Выдача результата

- Сохранить diff, explanation, validation decision, до/после Evidence, test log и итог.
- Исходный FinalReport не переписывать.
- Кнопка «Проверить исправление» работает только для подходящего confirmed и включенного оператором режима.
- Выдавать патч для review/скачивания. Автоматический commit, push, PR и merge в целевой репозиторий требуют отдельной авторизации и не являются частью первого MVP.
- Непринятый патч не снижает severity и не снимает первоначальный Gate.

### Тесты P6

- Исходный проект не изменяется даже при failed patch/check.
- Подмена пути через old/new header, rename, symlink и snapshot mismatch отвергается.
- Выполнение Python/Node target-кода происходит в Docker, не в host subprocess.
- Подмена approved diff запрещена.
- Патч, удаляющий проверку, не проходит validation.
- Простая печать «passed» не создает verified Evidence.
- Broken build, surviving defect и unavailable runtime дают разные объяснимые исходы.
- Положительный функциональный контроль ловит «исправление» удалением endpoint.
- После cancellation освобождаются только fix-ресурсы этого run.

### Критерий приемки

Один реальный подтвержденный дефект проходит полный процесс до проверенного патча в копии или честно отвергнутой попытки с доказательствами. Для демо автоисправления нужен именно успешный verified случай; если такого результата нет, показываем предложение патча как отдельную незавершенную возможность.

## 12. Этап P7. Скоринг без выдуманных значений

Оценка: 4–8 часов. Основной исполнитель: Леха; интеграция Ставра.

### CVSS

- Сначала выбрать несколько проверенных классов, для которых можно обосновать метрики.
- Отделить scanner severity от technical CVSS severity в API, отчетах и evaluation.
- LLM может предложить значения отдельных метрик с обоснованием, приложение проверяет допустимость; итоговый вектор/score считает детерминированный компонент.
- При неизвестных значимых фактах оставить UNASSESSED; hardening applicability оставить отдельной.
- Difficulty задач Juice Shop не переводить в CVSS.
- Для оценки создать независимую экспертную разметку с объяснением предпосылок, не называть ее официальным CVSS эталоном Juice Shop.
- Покрыть известными расчетными векторами, несовместимыми входами и отсутствующими данными.

### Context Priority

- Переиспользовать существующий deterministic scoring.
- Добавлять только source/runtime facts с происхождением: exposure, sensitive asset, DB access, guards, reachable critical component.
- Неизвестное остается неизвестным, не превращается в guessed HIGH/LOW.
- Заморозить веса до оценочных прогонов; отдельно проверить чувствительность к изменениям.
- Эталон размечать по заранее согласованной рубрике, желательно вторым человеком.
- При недостаточных фактах показывать reasons и ограничение полноты; не обещать надежную оценку всей архитектуры.

### Критерий приемки

На части набора есть воспроизводимый numeric CVSS и независимый reference. Для обеих оценок публикуются accuracy и coverage, так что малое число оцененных случаев не маскируется красивым процентом.

## 13. Этап P8. Интерфейс и демонстрационный сценарий

Оценка: 3–6 часов. Основной исполнитель: Ставр.

### Что должно быть видно

- Discovery и область анализа.
- Поиск по исходникам: шаг, файлы, source-context coverage, кандидаты, причина остановки.
- Источники finding: SAST, Scout либо оба; маршрут и source anchor.
- Статус гипотезы и точная причина inconclusive.
- Для каждого активного действия: цель, tool/безопасно отображенная команда, Validator decision, начало/конец, session, timeout/exit code, ограниченный output, артефакт.
- Доказательства отдельно от текста интерпретации.
- Scope подтверждения: исходное условие или runtime-наблюдение.
- Патч: diff, validation, результаты тестов, before/after, проверен/не проверен.
- Прогресс не перескакивает назад из-за позднего SSE события; summary идет после фактического окончания соответствующих этапов.

### Что не нужно делать

- Не переписывать весь дизайн.
- Не переводить имена API/команд/файлов, которые должны оставаться точными.
- Не выдавать сырой технический словарь без русского объяснения.
- Не добавлять streaming «мысли», если это не проверяемые действия/факты.

### Проверки UI

- Unit tests timeline/format и контракт новых событий.
- Build и TypeScript check.
- Markdown, code blocks, diff и длинные названия не разрушают верстку.
- Страница Runs работает на широкой и узкой ширине без горизонтального расползания.
- Перезагрузка страницы восстанавливает состояние из API, а не только из памяти браузера.
- Failure, partial result, cancellation и reconnect показываются отдельно.

### Сценарий демо

1. Открыть закрепленный проект и показать разрешенную область.
2. Запустить анализ; показать SAST и дополнительное source exploration.
3. Раскрыть конкретную находку и связь с обработчиком/маршрутом.
4. Показать одобрение политики и реально выполненную ограниченную проверку.
5. Показать Evidence и честный scope confirmed.
6. Если P6 прошел приемку: запросить исправление, показать diff и проверку до/после.
7. Скачать отчет/патч и назвать текущие ограничения.

Для встречи 9 октября подготовить короткий живой сценарий и сохраненный отчет настоящего запуска как резерв. Резерв маркируется «сохраненный запуск», а не выдается за live исполнение.

## 14. Этап P9. Эталон, baseline и метрики

Оценка: 6–12 часов, включая разметку; время трех полных прогонов добавляется отдельно. Исполнители: Леха + независимый reviewer, сбор артефактов Ставр/Кирилл.

### P9.1. Зафиксировать протокол до финальных запусков

- Точная версия и commit target, digest source snapshot, агентный commit и manifest локальных изменений.
- Область: приложение и поддерживаемые классы; excluded/unobservable cases перечислены.
- Единица оценки: независимый дефект/контроль, не строка отчета, не название challenge и не «срабатывание».
- Каждый reference case: stable case ID, family, anchors/handler, security expectation, предусловия, vulnerability label, допустимое доказательство.
- Для severity/Context Priority: независимые labels и основание; missing label не угадывать.
- Положительные и отрицательные случаи. Отрицательные должны включать настоящие защитные реализации, а не только тестовые JWT-литералы.
- Неподдерживаемые категории входят в inventory эталона; scoped denominator фиксируется до прогонов. Не исключать трудные случаи после просмотра результатов.
- Ground truth хранить отдельно от модельного корпуса, payload, target-visible artifacts и execution mounts.
- Development набор для настройки отделить от holdout оценки; если независимого holdout нет, явно назвать результаты development evaluation.

### P9.2. Исправить evaluation

В существующих schemas/evaluation.py и evaluation/runner.py:

- Убрать требование минимум двух targets, если оцениваем один закрепленный Juice Shop; не создавать фиктивный второй target.
- Добавить versioned case mapping: family + semantic anchor + ручное разрешение неоднозначности. Не полагаться на exact finding ID, который зависит от детектора.
- Учесть missing findings как пропуски в end-to-end метриках, не исключать их из accuracy denominator.
- Severity сравнивать с report.cvss.severity, а не scanner severity в report.finding.severity.
- Проверить уникальность ID и many-to-one matches. Один дефект не становится несколькими TP из-за нескольких сигналов.
- Unmatched confirmed отправлять на отдельное blinded review; до ревью их ground truth unknown, не автоматический TP или FP.
- Не менять замороженный recall oracle постфактум для улучшения цифр. Новые действительно найденные дефекты публиковать отдельно и использовать в следующей версии эталона.
- Разделить технический сбой, policy blocked, missing, inconclusive и отрицательный вердикт.
- Сохранить numerator, denominator, exclusions и mapping для каждой величины.
- Добавить unit tests метрик на полностью контролируемой маленькой таблице случаев, включая дубли и нулевые знаменатели.

### P9.3. Какие именно метрики считаем

| Метрика | Определение | Обязательное пояснение |
|---|---|---|
| Precision confirmed | TP / (TP + FP) | На adjudicated подтверждениях, отдельно число unknown/unreviewed confirmed и review coverage |
| Detection recall | Эталонные positive с кандидатом / все positive фиксированного scope | Показывает поиск, еще не доказательство |
| Confirmation recall | Эталонные positive с достаточным confirmed / все positive фиксированного scope | Основной end-to-end recall; missing/inconclusive не исчезают из знаменателя |
| FPR окончательных решений | FP / (FP + TN), TN = корректный rejected отрицательного случая | При отсутствии решенных negative знаменатель нулевой, результат N/A |
| False-confirmation на всех negative | FP / все negative | Дополнительно указывать negative abstention; не называть inconclusive true negative |
| Доля ложных подтверждений | FP / (TP + FP) | Это 1 − precision, не подмена FPR |
| End-to-end verdict accuracy | Correct confirmed/rejected / все reference cases | Missing/inconclusive/policy/error показываются отдельно и не считаются правильными binary решениями |
| Accuracy среди решенных | Correct / случаи с confirmed/rejected | Только рядом с decision coverage, иначе легко скрыть массовый abstention |
| Severity accuracy | Совпавшие CVSS labels / оцененные случаи с reference | Также overall coverage и число UNASSESSED; можно дополнительно exact vector/score error |
| Context Priority accuracy | Совпавшие уровни / случаи с независимым reference и оценкой | Замороженная рубрика/веса; дополнительно confusion matrix и coverage |
| MTTR | Время до реально принятого/внесенного исправления по записям процесса | Пока таких записей нет: N/A; не заменяем временем анализа или verified patch в копии |
| Time to verified patch | От подтверждения до проверенного патча в лабораторной копии | Новая техническая метрика автоисправления, не реальный MTTR |
| Воспроизводимость | Совпадение найденных/подтвержденных semantic cases между независимыми runs | Стабильный вход, одинаковые бюджеты, фактическое число прогонов |

Если требуется другой FPR convention для системы с abstention, его согласуют до запуска. В отчете остается полная таблица исходов отрицательных случаев, из которой можно пересчитать оба варианта.

### P9.4. Baseline и контроль вклада компонентов

Минимальные режимы с одинаковым snapshot, областью и эталоном:

1. SAST отдельно, фиксированный ruleset и exclusions.
2. DAST отдельно, фиксированный инструмент, seeds/fixtures и разрешенный бюджет.
3. SAST + DAST без Scout, контекстного ранжирования и агентной переоценки.
4. Полный агент: SAST + Scout + доступные проверки + Context Priority.

Важно: scanner alert не автоматически confirmed. Scanner modes имеют detection outputs и оцениваются по reference; окончательные доказательства сравниваются отдельно.

Дополнительные ablation для недельного этапа:

- Без Scout при тех же verifier.
- Со Scout, но без route map.
- С route map и полным verifier.
- С одинаковым фиксированным набором кандидатов: Context Priority ranking против neutral order при одинаковом verification budget.

Последний режим нужен, чтобы не смешать пользу приоритизации с дополнительными проверками или большим бюджетом. Для него полезны confirmed findings на единицу времени и recall при фиксированном deadline.

### P9.5. Три настоящих полных прогона

- После заморозки кода и протокола выполнить три независимых запуска с чистым target state и новыми run/session IDs.
- Не менять prompt, маршруты, бюджеты, эталон и веса между ними. Если пришлось исправить код, это новая серия, а предыдущая development.
- Не выдавать cached/resumed findings за независимое повторение.
- Сохранить выбранные model IDs, настройки sampling при поддержке, fallback events, ошибки и токены при доступности.
- Для каждого run сохранить duration, результаты по case, artifacts и все denominators.
- Показать каждый run, mean, min/max; confidence intervals/вариативность подписывать с учетом малого числа запусков.
- Для воспроизводимости посчитать set overlap/Jaccard отдельно для detected и confirmed, долю одинаковых вердиктов и разброс длительности. Даже три runs не доказывают качество на произвольных проектах.

### Критерий приемки

Метрики воспроизводятся из сохраненных JSON одним evaluation-процессом. Из таблицы видно число cases, unknown, missed и abstained. Независимый проверяющий может восстановить происхождение любого TP/FP. Если DAST/scoring/repeats не выполнены, соответствующий пункт остается N/A, не имитируется.

## 16. Изменения общих контрактов

Перед каждой общей schema migration:

1. Найти всех потребителей в agent, app, Validator, Executor, Evidence, reporting, evaluation, API и frontend.
2. Зафиксировать значение поля, producer и trusted/untrusted origin.
3. Добавить version/default или явную миграцию старых artifacts.
4. Обновить unit/contract tests и frontend types.
5. Проверить, что schema addition не разрешила новые параметры старым capabilities.
6. Прогнать старые deterministic E2E и deny regressions.

Возможные новые общие данные: source anchors, route binding, detection provenance, semantic fingerprint, fix scope и временные метки. Они не должны становиться второй версией Finding/FinalReport в локальном модуле.

## 17. Зависимости и порядок исполнения

```text
P0 проверенная база
 ├─ P1 надежный Scout ─ P2 карта кода ─ P3 merge/bindings ─ P4 проверки
 │                                                   └─ P7 scoring
 ├─ P5 бюджеты/lifecycle, идет параллельно и нужен P4/P6
 └─ P9 эталон/протокол, начинается сразу

```

Не ждем окончания всех модулей для подготовки эталона. Не запускаем финальную серию, пока меняются prompt, bindings и evaluation conventions.

## 18. Приоритеты на сегодня и на неделю

### Реалистичный минимум для ближайшего демо

1. Проверенная исходная точка и работающая модель.
2. Чистый source-only запуск, просмотр всех кандидатов и сопоставление с SAST.
3. Ограниченная route map для выбранных handlers, а не полный анализ всего приложения.
4. Один-два зрелых класса проверки с понятным Evidence.
5. Понятный UI и настоящий сохраненный отчет.
6. Безопасный fix цикл для одного класса только если прошли его isolation и before/after acceptance.

Если времени не хватает, сокращаем число поддерживаемых классов. Не сокращаем изоляцию, отрицательные проверки и достаточность доказательства. Лучше показать честно рабочий поиск/подтверждение и diff proposal, чем назвать непроверенный патч исправленным.

### Недельная программа

- День 1: P0/P1, старт oracle, ограниченная карта, демо search/verification.
- День 2: P2/P3, полноценный trusted binding поддерживаемых маршрутов.
- День 3: SQL/files verifier, protected controls, надежность.
- День 4: read-only access control, fixtures, scoring reference.
- День 5: sandbox fix цикл одного класса и интерфейс.
- День 6: freeze, baseline, настоящие полные повторы.
- День 7: независимое ревью, расчет метрик, отчет и интеграция.

Это ориентир при параллельной работе команды. Один разработчик последовательно не выполнит весь недельный объем за несколько часов. Финальные runs планируются по фактически измеренной длительности, с запасом на preflight и cleanup.

## 19. Распределение работы

| Ответственный | Основные задачи | Что передает остальным |
|---|---|---|
| Ставр | Scout, карта исходников, graph integration, merge, UI | Контракты bindings/provenance, очередь findings, объяснимый E2E |
| Рома | Validator, eligibility проверки/патча, Evidence semantics, negative controls | Политика параметров, критерии confirmed/rejected/verified, deny tests |

## 20. Коммиты и приемочные ворота

Логические delivery checkpoints:

1. Проверка текущего Scout и регрессии последнего изменения.
2. Политика корпуса, coverage и память.
3. Route/source map и trusted binding.
4. Provenance, fingerprints и dedup.
5. Один verifier class с Validator/Evidence и positive/negative тестами.
6. Deadlines/lifecycle, устранение host execution из fix product path.
7. Patch validation и isolated before/after.
8. UI и API контракты.
9. Evaluation semantics и frozen dataset.
10. Проверенные benchmark artifacts и документация результатов.

Перед каждым commit: targeted tests, Ruff/diff check, просмотр staged paths. Не добавлять .env, credentials, .venv, node_modules, pyc, tmp и диагностический мусор. Не удалять посторонние файлы без отдельного решения.

Перед merge в main: полная suite, `python -m app.main`, Ruff, frontend tests/build и необходимые Docker E2E. Если remote/auth недоступны, локальный результат не называется успешно pushed/merged.

## 21. Риски и заранее выбранные ограничения

| Риск | Что делаем |
|---|---|
| Модель недоступна или изменился ID | Preflight, ограниченный fallback, сохранение частичных результатов; без смены ключей/провайдера молча |
| Scout возвращает больше шума | Protected controls, более точный source/route context; не повышаем confirmed quota искусственно |
| Парсер не понимает динамический middleware | Unknown + bounded source review, не «guard отсутствует» |
| Runtime verifier не покрывает семейство | Явный unsupported reason, отдельная очередь расширения |
| Область benchmark слишком мала | Publish scoped metrics и inventory остального; не называем это полным recall Juice Shop |
| Переполнение budget | Сохраняем partial result и stop reason, не заявляем отсутствие других дефектов |
| Патч ломает приложение | Положительный функциональный контроль, сборка/тесты, rollback уничтожением копии |
| Патч подменяет verifier | Trusted verifier остается вне target patch scope и не изменяется моделью |
| Demo deadline | Сокращаем семейства, используем честный сохраненный run, не выключаем безопасность |
| Конфликты с командой | Малые изменения, явные interfaces, selective staging, без destructive Git-команд |

## 22. Что считаем завершением

### Поиск завершен как этап разработки, когда

- Корпус и исключения воспроизводимы и не содержат oracle/решения.
- Кандидаты имеют прочитанные anchors и происхождение.
- Бюджеты, память и причины остановки проверены.
- Route/guard context для поддерживаемого стека сохраняется; unknown не скрыт.
- Merge не теряет независимые дефекты и происхождение.

### Проверка готова, когда

- Нет зависимости от ручного описания каждой строки для поддерживаемых классов.
- Активные действия проходят Validator и registered Executor.
- Есть положительные и защищенные отрицательные случаи.
- Terminal statuses определяются достаточными Evidence в точном scope.
- Ошибки не зависают и не теряют результаты.

### Автоисправление готово к демо, когда

- Патч предлагается по confirmed и применим к конкретному snapshot.
- Его scope проверен кодом.
- Generated/target code не выполняется на хосте.
- До/после воспроизводится исходная проверка и сохраняется нужная функциональность.
- Исходный проект и исходный отчет не изменены.
- Пользователь получает проверенный diff и доказательства, не обещание автоматического merge.

### Недельная работа готова к передаче Сергею, когда

- Зафиксированы target, агент, конфигурация, oracle, matching и бюджеты.
- Выполнены заявленные baseline и реальные независимые повторы.
- Полные case outcomes доступны и арифметика воспроизводима.
- Precision/recall/FPR/accuracy не смешивают разные наборы без подписи.
- Scoring coverage и abstention показаны рядом с accuracy.
- MTTR остается N/A без реального процесса принятого исправления; время до лабораторного патча подписано отдельно.
- Отчет отделяет development результаты, holdout и неподдерживаемые категории.

## 23. Первая конкретная реализация после утверждения плана

Не начинаем с нового общего промпта и не включаем небезопасный fix service в чат.

Порядок ближайших действий:

1. P0: проверить текущие Scout/backend/frontend изменения и модельный structured preflight.
2. P1: исправить выявленные регрессии, полный audit early exits и candidate cap, зафиксировать clean corpus.
3. Запустить чистый Scout на закрепленном Juice Shop и разобрать каждый кандидат; это development run, не финальный benchmark.
4. По конкретным проблемам кандидатов реализовать минимальный P2 source map: маршруты, порядок guards, handlers.
